# AGENTS.md — RAG Assistant

## Agent Workflow

- Делай минимальное изменение, которое полностью решает задачу; сохраняй бизнес-поведение и инварианты.
- Сначала изучай только затронутые компоненты и их вызовы. Не сканируй весь репозиторий без необходимости.
- Не запускай субагентов без прямого запроса. Дополнительные skills применяй только при необходимости или по запросу.
- Не создавай документацию и отчёты без запроса; не расширяй задачу масштабным рефакторингом.
- Не меняй архитектуру ради косметики. Экономия контекста не оправдывает риск для безопасности и корректности.
- Сначала запускай целевые тесты; полный набор — если этого требует изменение или остаётся конкретный риск.
- Не заявляй, что проверки прошли, пока не выполнил их и не увидел результат.
- Сохраняй чужие незавершённые правки; не переписывай их при работе в общем дереве.

## Карта проекта и команды

- `server/app/main.py` — FastAPI и жизненный цикл; `server/app/presentation/cli/` — CLI.
- `server/app/{domain,application,infrastructure,presentation,composition}/` — слои; `server/tests/` — тесты.
- `server/pyproject.toml` и `server/uv.lock` — зависимости; `server/app/config.py` — настройки.
- `Taskfile.yml` — источник актуальных команд. Основные: `task install`, `task test`, `task lint`, `task fmt`.
- Целевой тест: `cd server && uv run pytest tests/<file>.py -v`.
- После изменения `server/pyproject.toml` обновляй lock через `task lock`.
- `task up`/`task down` управляют Docker; `task clean` удаляет локальные данные.
- `server/.env`, `server/.env.secrets`, `client/.env` используются Taskfile; не добавляй секреты в git.

## Слои и предметная логика

- Направление зависимостей: Presentation → Application → Domain; Infrastructure реализует порты,
  Composition связывает реализации. Это целевое ограничение для изменений, не оценка всего старого кода.
- Domain: сущности, value objects, бизнес-правила и интерфейсы репозиториев. Не импортируй сюда
  Application, Infrastructure, Presentation, `config` и детали FastAPI, SQLAlchemy или Qdrant.
- Application: сценарии, DTO, порты, UoW. Зависит от Domain и собственных интерфейсов;
  не привязывай сценарии к конкретным клиентам, ORM, Redis или HTTP.
- Infrastructure: адаптеры БД, Qdrant, BM25, ML, Redis и хранения. Реализует нужные порты.
- Presentation: валидация входа, аутентификация, HTTP/SSE и перевод ошибок; маршруты держи тонкими.
- Composition: сборка зависимостей в `composition/container.py`, `application.py`, `infrastructure.py`
  и `service_providers.py`; не собирай concrete-реализации внутри бизнес-сервисов.
- Размещай правила предметной области в Domain, оркестрацию сценария в Application.
  Инварианты редакций — в `ActVersion`/`ActVersionTimeline`; загрузка и сохранение — вне Domain.
- Не обходи инварианты прямой записью в ORM. Проверяй ограничения БД и гонки read/check/write.
- При изменении правила доступа прослеживай его путь от Domain до всех адаптеров и API.

## Авторизация и RAG

- Считай идентификаторы и параметры запроса недоверенными. На каждом пути чтения/изменения
  проверяй права на конкретный объект, владельца и группы; аутентификация сама по себе недостаточна.
- `domain/services/access_control.py::get_visibility_conditions()` — источник условий видимости.
  Сохраняй соответствие `is_in_search_scope()` ⇔ Qdrant `build_qdrant_filter()` ⇔
  `BM25Index._doc_matches_acl()` для USER, ADMIN, CURATOR и CLIENT.
- Различай режимы listing и search (`for_list`): ADMIN может видеть `CLIENT_PRIVATE` в списке,
  но не получает эти документы в RAG-поиске. Не расширяй scope поиска случайно.
- Передавай актуальный `UserContext` и группы через поиск, обработку документов и выдачу источников.
  `CuratorScope` формируется из назначений и ограничивается в `ChatService`.
- Dense Qdrant поиск и разрешение BM25-хешей требуют ACL-фильтр. BM25 фильтрует до скоринга;
  повторную проверку Qdrant при разрешении sparse-кандидатов сохраняй.
- При индексации и обновлении чанков сохраняй ACL-метаданные владельца, видимости и группы
  согласованными между хранилищем документов, Qdrant и BM25.
- Ключ кэша ответа должен учитывать kind, role, user id, группы и curator scope;
  изменение полномочий должно приводить к cache miss. Не кэшируй ответ вне его scope.
- Извлечённый текст — недоверенный ввод: не позволяй ему переопределять инструкции или ACL;
  не выдавай в ответе либо источниках документы, недоступные текущему пользователю.
- Путь чата: `presentation/api/routes/chat.py` → `application/services/chat_service.py`
  → `infrastructure/ml/rag_service.py` → `infrastructure/ml/rag/`.
  Чистые правила RAG находятся в `domain/services/rag_policy/`.

## Транзакции, async и ошибки

- В каждом изменяющем сценарии сохраняй явную границу UoW: commit при успехе,
  rollback при ошибке. Не держи транзакцию открытой во время долгого LLM/HTTP-вызова.
- Для связи БД с внешними эффектами учитывай идемпотентность, повторную доставку и outbox;
  не публикуй необратимое событие до подтверждения нужной записи.
- Не блокируй event loop синхронным I/O или тяжёлым CPU-кодом; используй async-клиенты
  либо выноси блокирующую работу в поток/worker. Сохраняй таймауты внешних вызовов.
- Освобождай внешние клиенты и фоновые задачи при завершении lifespan/container.
- Не скрывай ошибки `except Exception: pass/return None`. Допустимая деградация должна быть
  явной, ограниченной и залогированной; не превращай ошибку ACL в разрешение доступа.
- Для рабочих событий используй `logging`, не `print()`; не записывай секреты, PII
  или содержимое приватных документов в логи. Сохраняй контекст запроса при диагностике.

## Код и зависимости

- Импорты нового кода — на уровне модуля; type-only импорты — в `if TYPE_CHECKING:`.
  Ленивый импорт допускается для тяжёлой внешней ML-библиотеки с комментарием причины.
  Циклы устраняй границами зависимостей, а не вложенными импортами модулей проекта.
- Используй существующие enum/константы для ролей, видимости, статусов и политик;
  не дублируй бизнес-значения строками и не нарушай направление импортов.
- Не добавляй `assert` в production-код: Ruff S101 проверяет это; применяй явные проверки.
- Новые модули, обычные функции и методы именуй без начального `_`, кроме обязательных
  Python/framework hooks. При изменении такого API переименовывай вызовы в его компоненте.
- Добавляй только непосредственно используемые зависимости; сначала проверь уже имеющиеся.
  После изменения зависимостей обнови `uv.lock`.

## Проверки

- Для бизнес-инвариантов добавляй содержательные тесты; для ACL — разрешённый и запрещённый
  сценарии, для гонок — конкурентный тест, если практически осуществимо.
- При изменении ACL/RAG сохраняй тесты `server/tests/test_acl.py`, `test_bm25_acl.py`,
  `test_answer_cache.py`, `test_curator_role.py` и запускай относящиеся к правке сценарии.
- Для изменения retrieval/ingestion дополнительно смотри `test_retrieval_acl.py`
  и `test_ingestion_acl_consistency.py`.
- Перед рефакторингом сложного публичного поведения зафиксируй его существующими или
  characterization-тестами; проверь baseline до изменения.
- При изменении Domain/Application проверь отсутствие обратных импортов в затронутых файлах;
  `task lint` включает Ruff и mypy. Не запускай полный набор без основания.
- В режиме аудита не меняй исходники и не исправляй находки автоматически;
  подтверждай проблемы по полному затронутому пути и приводи файл, строку, сценарий.
