# Блокирующий код в event loop — как искать

Ищи в `async def` функциях (эндпоинты, use case, репозитории) вызовы:
- `requests.*` (синхронная HTTP-библиотека) вместо `httpx.AsyncClient`/
  `aiohttp`.
- `time.sleep(...)` вместо `await asyncio.sleep(...)`.
- Синхронные SDK клиентов LLM-провайдера или векторной БД, если у них есть
  async-вариант (`client.chat.completions.create` вместо
  `await client.chat.completions.create` / отдельный `AsyncClient`).
- CPU-тяжёлые операции без выноса в executor: парсинг больших PDF,
  токенизация больших текстов, генерация эмбеддингов локальной моделью на
  CPU — должны идти через `loop.run_in_executor(...)` или отдельный
  процесс/воркер, иначе блокируют весь event loop и всех конкурентных
  пользователей на время операции.
- Синхронный ORM (`Session.query(...)`) в async-обработчике вместо
  `AsyncSession`.

Один блокирующий вызов на 2-3 секунды в популярном эндпоинте RAG-чата
(например, синхронный вызов embedding API) означает, что **все**
остальные пользователи, чьи запросы попали в тот же event loop/воркер,
ждут эти 2-3 секунды, даже если их запрос ничего общего с этим вызовом не
имеет.

# Пулы соединений и клиенты

- [ ] `engine`/пул соединений к БД создаётся один раз при старте
      приложения (singleton), а не на каждый запрос.
- [ ] Размер пула (`pool_size`, `max_overflow`) сопоставлен с числом
      воркеров/процессов и ожидаемой конкурентностью — типичная ошибка:
      пул на 5 соединений при 20 uvicorn/gunicorn воркерах → постоянные
      "QueuePool limit exceeded" под нагрузкой.
- [ ] HTTP-клиент к LLM-провайдеру и к векторной БД переиспользуется как
      singleton с connection pooling (`httpx.AsyncClient` с
      `limits=httpx.Limits(...)`), а не создаётся заново на каждый запрос.

# Фоновые задачи

- [ ] Тяжёлые операции (ingestion большого документа, batch-переиндексация
      базы знаний, пересчёт эмбеддингов при смене модели) вынесены из
      HTTP request-response цикла в очередь задач (Celery/ARQ/Dramatiq/RQ)
      или как минимум в `BackgroundTasks` для лёгких случаев.
- [ ] У фоновых задач есть retry-политика и идемпотентность: повторный
      запуск после сбоя не создаёт дублирующихся чанков/эмбеддингов.
- [ ] Конкурентность фоновых задач ограничена на тенанта (rate/concurrency
      limit), чтобы один клиент, загрузивший тысячи документов разом, не
      занял всю очередь для остальных.
- [ ] Фоновые задачи корректно управляют своими ресурсами (открывают и
      закрывают собственную DB-сессию/HTTP-клиент, не полагаясь на
      FastAPI `Depends`, который в них не работает).

# Таймауты, ретраи, circuit breaker для внешних вызовов

- [ ] У каждого вызова к LLM-провайдеру и к векторной БД задан явный
      таймаут (connect + read) — их отсутствие означает, что зависший
      внешний сервис вешает воркер/соединение бесконечно.
- [ ] Ретраи применяются только к транзиентным ошибкам (5xx, 429,
      network timeout) с экспоненциальным backoff и джиттером — ретраи
      4xx (кроме 429) или ошибок валидации/авторизации бессмысленны и
      вредны (маскируют реальную проблему, увеличивают задержку и
      стоимость).
- [ ] Есть механизм graceful degradation при деградации LLM-провайдера:
      circuit breaker, fallback-ответ, очередь с ограничением, а не
      каждый запрос ждёт полный таймаут по несколько раз подряд.
- [ ] Rate limit провайдера обрабатывается на уровне приложения
      (внутренняя очередь/семафор на конкурентные вызовы), а не только
      реактивными ретраями после 429.

# Кэширование

- [ ] Эмбеддинги для неизменного контента не пересчитываются повторно
      (кэш по хэшу содержимого чанка).
- [ ] Если есть кэш ответов LLM/результатов retrieval — учитывай, что его
      ключ обязан включать tenant_id/user_id, если ответ зависит от них
      (пересекается с областью multi-tenant безопасности — при находке
      сразу отметь это).

# Наблюдаемость

- [ ] Request ID / trace ID генерируется на входе и пробрасывается через
      все слои, включая фоновые задачи и логи ошибок LLM/векторной БД.
- [ ] Есть трейсинг (OpenTelemetry или аналог) для стадий RAG-пайплайна
      (retrieval, prompt building, generation) — без него невозможно
      локализовать узкое место под нагрузкой.
- [ ] Собираются метрики: латентность по стадиям, количество
      входных/выходных токенов и стоимость на запрос (в идеале — с
      разбивкой по tenant_id для контроля costs), доля
      ошибок/таймаутов от внешних провайдеров.

# Как оформлять находки

Для каждой находки укажи конкретный сценарий деградации под нагрузкой
("N одновременных пользователей → блокирующий вызов X держит event loop Y
мс → эффективный throughput падает до Z RPS"), а не только абстрактное
"это неэффективно".
