# Способы DI — как распознать в проекте с самописным контейнером

Раз стороннего DI-фреймворка нет, "контейнер" — это ваш собственный
класс/модуль (`Container`, `Registry`, `Providers`, `AppState`),
который где-то регистрирует фабрики/инстансы и где-то их отдаёт. Способ
интеграции с FastAPI определяет, насколько это остаётся настоящим DI, а
не превращается в service locator:

| Признак в коде | Оценка |
|---|---|
| `def get_x() -> X: return container.x()`, используется как `Depends(get_x)` | ✅ Правильно: контейнер — фабрика, инъекция всё равно идёт через `Depends`, тестируется через `app.dependency_overrides` |
| `container.x` — обычный **дескриптор/property** ("provider"), но каждый provider явно обёрнут своей `Depends`-функцией | ✅ Приемлемо, если провайдеры именованы по ролям, а не как generic `resolve(Any)` |
| `request.app.state.container.resolve(X)` вызывается прямо внутри тела эндпоинта/сервиса | ⚠️ Service Locator — зависимость спрятана, не видна в сигнатуре, не подменяется штатным `dependency_overrides` |
| `container.get(X)` / `container.resolve(X)` внутри domain/application кода | ⚠️⚠️ Service Locator **внутри бизнес-логики** — худший случай, домен узнаёт о существовании контейнера |
| Глобальный модульный синглтон, импортируемый напрямую (`from container import container`, `from db import engine`) | ⚠️ Скрытая глобальная зависимость — не виден потребителям через сигнатуру конструктора |

**Service Locator vs DI:** при DI зависимость приходит как параметр
конструктора/функции — вызывающий код не знает, *как* она создана. При
Service Locator код сам явно "идёт и достаёт" зависимость из контейнера
по требованию — это прячет реальные зависимости класса, усложняет тесты
и создаёт скрытые связи между модулями. Правило простое: **если у
самописного контейнера есть публичный `resolve`/`get`, единственное
место в проекте, где он должен вызываться — это Depends-обёртки в
composition root.** Любой другой вызов `resolve`/`get` — находка.

# Особенности именно самописного (без библиотек) контейнера

Готовые библиотеки (dependency-injector, punq, dishka и т.п.) бесплатно
дают: валидацию графа на старте, обнаружение циклов, потокобезопасный
lazy-singleton, встроенный override для тестов. Самописный контейнер
ничего из этого не гарантирует автоматически — проверяй руками:

- **Валидация графа при старте.** Есть ли явная проверка "все
  зарегистрированные провайдеры реально резолвятся" при запуске
  приложения, или ошибка отсутствующей/неправильной зависимости
  всплывёт только в рантайме на первом реальном запросе (в худшем
  случае — только под конкретным edge-case сценарием в проде)?
- **Обнаружение циклов.** Библиотеки обычно кидают понятную ошибку при
  регистрации циклической зависимости. У самодельного решения без такой
  проверки цикл A→B→A может либо уйти в `RecursionError` в рантайме,
  либо быть "разрешён" костылём (поздний `setattr` на
  незаинициализированный объект) — ищи такие костыли отдельно, это явный
  признак того, что граф зависимостей не спроектирован, а подогнан.
- **Потокобезопасность/async-безопасность lazy-singleton.** Типичная
  наивная реализация:

  ```python
  class Container:
      _qdrant_client: QdrantClient | None = None

      def qdrant_client(self) -> QdrantClient:
          if self._qdrant_client is None:
              self._qdrant_client = QdrantClient(url=settings.qdrant_url)
          return self._qdrant_client
  ```

  Под конкурентной нагрузкой два запроса могут одновременно увидеть
  `None` и оба создать клиента. Для простого сетевого клиента вроде
  `QdrantClient`/`httpx.AsyncClient` двойная инициализация обычно не
  катастрофична (лишний объект, лишнее соединение), но если такой же
  паттерн применён к чему-то с side-effects при создании (открытие
  файла, аллокация лока, регистрация в внешнем реестре) — это гонка.
  Правильнее: инициализировать синглтоны **явно на старте приложения**
  (`FastAPI` lifespan/`startup`-событие), а не лениво по требованию.
- **Отсутствие штатного override для тестов.** У вашего контейнера
  должен быть явный способ подменить провайдер в тестах (метод
  `container.override(X, fake)` / отдельный `TestContainer` подкласс /
  фабрика `build_container(settings=test_settings, qdrant_client=fake)`).
  Если такого механизма нет и тесты вместо этого делают
  `unittest.mock.patch("app.container.container")` — это находка: patch
  по строковому пути хрупок к рефакторингу.

# Время жизни зависимостей (lifetime)

| Тип ресурса | Обычно должен быть |
|---|---|
| Конфиг/настройки (`Settings`) | Singleton, инициализирован на старте приложения |
| `QdrantClient` (HTTP/gRPC клиент к Qdrant) | Singleton (с переиспользуемым pooled-соединением), инициализирован в lifespan |
| HTTP-клиент к LLM-провайдеру / embedding-сервису | Singleton (с connection pooling) |
| `AsyncSession`/DB-соединение | Request-scoped (создаётся и закрывается на запрос) |
| Current user / tenant context | Request-scoped |
| Unit of Work | Request-scoped (или per-use-case) |
| Value Object / DTO | Transient (создаётся каждый раз заново) |

## Частые нарушения и их последствия
- **Singleton там, где нужен request-scoped** (например, `AsyncSession`
  или "текущий пользователь" объявлены как singleton в DI-контейнере):
  под конкурентной нагрузкой запросы разных пользователей начинают
  делиться состоянием — от гонок в транзакциях до **утечки данных между
  пользователями/тенантами**, если singleton хранит tenant-контекст.
- **Request-scoped/transient там, где нужен singleton** (пересоздание
  тяжёлого HTTP-клиента или embedding-модели на каждый запрос): лишние
  TLS handshake, потеря connection pooling, деградация производительности
  под нагрузкой, риск исчерпания файловых дескрипторов/сокетов.
- **Незакрытые ресурсы:** провайдер зависимости без `yield` +
  `finally`/`async with` для сессий БД, файловых хендлов, HTTP-клиентов —
  утечка соединений под нагрузкой.

# Проверка через FastAPI generator-dependency

Правильный паттерн управления ресурсом:

```python
async def get_db_session() -> AsyncIterator[AsyncSession]:
    async with async_session_factory() as session:
        try:
            yield session
        finally:
            await session.close()
```

Признак проблемы: `Depends`, возвращающий сессию через `return`, а не
`yield` — она не будет закрыта FastAPI автоматически по завершении
запроса.

# Циклические зависимости

Ищи ситуации:
- `ServiceA.__init__` принимает `ServiceB`, а `ServiceB.__init__`
  принимает `ServiceA` (напрямую или через интерфейс) — даже если ваш
  самописный контейнер технически смог их разрешить (например, через
  двухфазную инициализацию — сначала создать оба "пустыми", потом
  досеттить друг друга через `setattr`) — это архитектурный запах и
  повод выделить общую логику в третий модуль/domain service, а не повод
  усложнять контейнер поддержкой такого сценария.
- Импорт по кругу между модулями регистрации провайдеров
  (`container_a.py` импортирует из `container_b.py` и наоборот).

# Тестируемость

- [ ] Внешние зависимости (LLM API, векторная БД, embedding-сервис, время
      `datetime.now()`, генератор UUID) внедряются как параметры/
      Depends, а не вызываются напрямую внутри бизнес-логики — это
      позволяет подменить их в тестах через `app.dependency_overrides`
      или конфигурацию контейнера для тестового окружения.
- [ ] Тесты не полагаются массово на `unittest.mock.patch("module.func")`
      там, где вместо этого стоило бы внедрить зависимость — patch по
      строковому пути хрупок к рефакторингу и говорит о том, что
      зависимость "зашита" в код, а не инжектится.
- [ ] Есть отдельная тестовая конфигурация DI-контейнера/фикстуры
      `overrides`, не пересекающаяся с production-конфигурацией по
      случайности импорта.

# Composition root

- [ ] Сборка графа зависимостей (создание экземпляра контейнера,
      регистрация провайдеров, `app.dependency_overrides`, чтение
      `Settings`) происходит в одном явном месте (`main.py`,
      `bootstrap.py`, `container.py`), а не размазана по модулям через
      побочные эффекты импорта (например, `container.register(X, ...)`
      на уровне модуля, выполняющийся только если этот модуль случайно
      был импортирован раньше composition root).
- [ ] Domain-слой не импортирует сам класс контейнера и не вызывает его
      `resolve`/`get` — иначе DI "протекает" в код, который должен быть
      framework-agnostic (см. также `ddd-architecture-reviewer`).
- [ ] Инициализация тяжёлых singleton-ресурсов (клиент Qdrant, HTTP-клиент
      к LLM) происходит в FastAPI `lifespan`/`startup`, а не лениво при
      первом запросе — это одновременно решает проблему thread/async-race
      при ленивой инициализации и даёт быстрый fail-fast, если, например,
      Qdrant недоступен при старте.

# Секреты и конфигурация

- [ ] Чтение `os.environ`/`.env` происходит только в слое конфигурации
      (`Settings` через `pydantic-settings` или аналог), а не разбросано
      по бизнес-коду через `os.getenv(...)` в случайных местах.
- [ ] Секреты (API-ключи LLM-провайдера, DSN БД) не логируются при ошибках
      инициализации DI-контейнера (частая ошибка: исключение с полным
      repr объекта настроек, содержащего ключ, попадает в лог/traceback,
      отданный клиенту).

# Конкретный DI в этом проекте

Для быстрого поиска проблем через grep используй следующие имена:

| Что | Где | Описание |
|---|---|---|
| `Container` | `composition/container.py:26` | Верхний уровень, `init(db)` / `dispose()` |
| `InfrastructureContainer` | `composition/infrastructure.py:267` | Sub-containers: Database, ML, Event, Service |
| `ApplicationContainer` | `composition/application.py:63` | 22+ сервисных поля |
| `DatabaseContainer` | `composition/infrastructure.py:55` | DB connection, UoW factory |
| `MLContainer` | `composition/infrastructure.py:87` | MLClientRegistry, vector store, file storage |
| `_require()` | `composition/_utils.py:15` | Guard: raises ContainerNotInitializedError |
| `service_providers.py` | `composition/service_providers.py` | CLI/worker фабрики |
| `dependencies.py` | `presentation/api/dependencies.py:50` | Depends-обёртки (container → FastAPI) |
| `tests/fakes.py` | `tests/fakes.py` (807 строк) | Fake repositories, UoW, ChatRAGPort |
| `tests/conftest.py` | `tests/conftest.py` | Фикстуры для подмены зависимостей |

**Паттерн доступа:** прямой атрибут (`container.application.chat_service`),
**НЕ** `resolve()`/`get()`. Если в коде встречается `resolve` или `get` —
это service locator.

**Тестирование:** подмена через фикстуры в `conftest.py` с фейками из
`tests/fakes.py`. Метода `container.override()` нет — это осознанный выбор
(явные фейки вместо автоматической подмены).
