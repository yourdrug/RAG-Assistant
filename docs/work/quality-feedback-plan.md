# План: журнал ответов, реакция пользователя и измерение качества RAG

Рабочий план. Не является источником истины о поведении системы; устойчивые решения переносить
в `docs/architecture/`, `docs/quality/` и ADR. Пути — от `server/app/`, если не указано иное.
Термины — [глоссарий](../domain/glossary.md): запись журнала, исход ответа, трасса запроса,
реакция пользователя, разбор записи.

Цель — замкнуть цикл качества:

```
вопрос → ответ + трасса → реакция пользователя → разбор в админке
      → вопрос в benchmark-набор → прогон → решение по изменению → выкатка
```

Части:

- **I. Журнал и обратная связь (п. 2 дорожной карты)** — этапы A–D. Начинаем с них:
  они дают данные для части II.
- **II. Измерение качества (п. 1)** — этапы E–H.

Общие правила:

- Система не в продакшене: миграции могут быть разрушающими. Существующие строки `chat_logs`
  очищаются миграцией этапа A (восстановить `outcome`, `space_id`, `message_id` честно нельзя).
- Каждый этап — отдельный PR с целевыми тестами; UI делается в том же этапе, что и данные.
- Не хранить в журнале и трассе секреты, ключи, текст системного промпта и текст чанков.
  Текст фрагментов показывается админке только по запросу и только после проверки
  прав *просматривающего* (см. этап B).
- Права на просмотр журнала не меняются: `Capability.SYSTEM_OBSERVE`; CURATOR видит только
  управляемых пользователей и себя (`routes/admin_chat_logs.py`). Все новые эндпоинты,
  включая трассы, повторяют это правило; отдельной capability для трасс нет.
- Пространства знаний уже реализованы ([план](knowledge-spaces-plan.md), этапы 1–5):
  `space_id` и `pack_key` заполняются сразу в этапе A, фильтр по пространству — там же.
- Все benchmark-вопросы живут только в БД. JSON-файлы с вопросами из пакетов удалены
  (импортированы 2026-11-17; дампы — `backups/benchmark-questions/`, локально).
  В пакетах остались только офлайн-подмножества `benchmarks/chunking/*.json` и `acceptance.json`.

## Текущее состояние (проверено по коду 2026-11-15)

Журнал: `domain/chat/chat_log.py`, `application/chat/logs.py`, `application/chat/service.py`,
`ChatLogModel` в `infrastructure/database/models.py`, `routes/admin_chat_logs.py`,
`client/src/pages/admin/chat-logs.tsx`.

Найденные дефекты и пробелы:

1. **Потоковый путь теряет классификацию.** `ChatService.stream_chat` игнорирует
   `PipelineMetaEvent`: `domain` не передаётся и записывается как `general`
   (`ChatLogService.create`), `breadth` — это запрошенный `depth`, а не фактическая ширина,
   `model_used` пуст.
2. **Синхронный путь теряет токены.** `sync_chat` передаёт `usage=None`, `depth=None`,
   хотя `RagResult` содержит `input_tokens`/`output_tokens`.
3. **Нет исхода ответа.** Cache hit, блокировка входа/выхода, out-of-domain, отказ
   relevance gate, grounded response и обычная генерация в журнале неразличимы.
   Причины уже вычисляются (`capture_completion(...)` в `infrastructure/ml/rag/rag_steps.py`),
   но живут только в benchmark-трассе.
4. **Журнал не связан с сообщением.** В `chat_logs` нет `message_id`, клиент не получает id
   сообщения ассистента (`MetaEvent`, `MessageResponse` в `client/src/shared/api/types.ts`) —
   реакцию не к чему привязать.
5. **Ошибки и обрывы не журналируются.** `persist_chat` вызывается после цикла потока;
   при исключении или отключении клиента не сохраняется ни запись журнала, ни сообщения беседы.
6. **Нет снимка настроек.** Невозможно понять, при каких `retriever_*`, весах RRF, порогах
   реранкера, модели и evidence profile получен ответ.
7. **Вводящие в заблуждение поля.** `retrieval_count = len(sources)` — это число источников
   в ответе, а не найденных кандидатов; `reranker_score` считается по источникам.
8. **Трасса есть только в benchmark.** `BenchmarkEvidence` (`infrastructure/ml/rag/benchmark_evidence.py`)
   собирает кандидатов, исключения с причинами, gates, бюджет промпта. Наличие
   `active_evidence` отключает кэш (`rag_steps.py`, `lookup`/`store`) — это единственное
   поведенческое отличие; проверки в `rag_reranking.py` только пропускают запись исключений.
9. **Админка.** Фильтры: пользователь, домен, даты, поиск. Нет карточки ответа, сортировки,
   фильтра по исходу/реакции, экспорта и переноса в benchmark.

Что уже есть и переиспользуется: per-question результаты benchmark (`benchmark_runs.per_question_results`),
`task bench:regression` (сравнение с baseline, exit 1), `task chunking:report` (офлайн-прокси),
CRUD, импорт и экспорт benchmark-вопросов (`routes/benchmark_admin.py`), поле `dataset` у вопросов,
версии runtime-конфигурации (`saved_version`/`applied_version`, ADR 0001).

# Часть I. Журнал и обратная связь

## Этап A. Исправить и обогатить запись журнала

**Статус: выполнен в коде (2026-11-17).** Миграция `0016_answer_attempts` подготовлена; применение к

**Цель.** Каждая попытка ответа (включая отказы, кэш, ошибки и обрывы) даёт полную запись:

**Запись журнала и сообщение.** Запись журнала — попытка ответа; сообщение ассистента —
доставленный ответ; связь 1:0..1.
- [x] Завершённые попытки (любой исход, кроме `error`/`cancelled`, включая `not_found`,
  блокировки и кэш) сохраняют вопрос и ответ в беседу и запись журнала с `message_id`.
- [x] `error`/`cancelled`: только запись журнала с частичным ответом, `message_id = NULL`;
  в истории беседы хода нет, оценить его нельзя.

**Domain.**
- [x] `domain/rag/outcome.py`: `AnswerOutcome(StrEnum)` — `generated`, `grounded` (ответ собран
  без LLM), `cache_hit`, `not_found` (любой отказ evidence gate), `out_of_domain`,

  `capture_completion`; используется и журналом, и benchmark (этап E).
  Один плоский исход на запись; какая проверка отказала — только в трассе.
  Переполнение бюджета промпта — `error` с `error_code=prompt_budget`.
- [x] `ChatLog`: новые поля (все nullable, кроме `outcome` и `space_id`):

  - [x] запрос: `depth_requested`, `as_of_date`, `condensed_query`, `sub_queries`, `refined_query`;
  - [x] результат: `outcome`, `error_code`, `breadth` (фактическая), `domain` (фактический), `confidence`,

**Application.**
- [x] `application/rag/stream_events.py`: `PipelineMetaEvent` дополнить `outcome`, `request_id`,

- [x] `ChatService.stream_chat`: обрабатывать `PipelineMetaEvent`. Границы записи:

## Этап B. Трасса запроса

**Статус: выполнен в коде (2026-11-17).** Миграция `0017_chat_log_traces` проверена на
отдельной временной PostgreSQL-БД; применение к рабочей БД — отдельный шаг.

Сборщик сохраняет прежнюю benchmark-трассу и выдаёт отдельную production-проекцию
`schema_version=1`. В production нет текста документов, промпта и истории. Пояснения gates
не возвращаются обычным GET: они доступны через POST фрагментов, только если проверены
все исходные фрагменты, их содержимое не изменилось и трасса не усечена. Это консервативная
проверка: при неполной идентификации или удалении фрагмента пояснения скрываются.

Проверки: целевые тесты RAG/benchmark/ACL/configuration, PostgreSQL-тесты миграции,
атомарности и retention, `task lint`, клиентский `npm run check`.
Замер записи на локальной временной PostgreSQL-БД: 45 транзакций на режим после прогрева,
40 кандидатов × 4 стадии, JSON 22 844 байта; медиана без трассы 1,20 мс, с трассой 2,40 мс,
разница +1,20 мс. Это замер записи и commit, без стоимости поиска/генерации и сбора трассы.

**Цель.** По каждой записи видно, что нашёл поиск, что отсёк реранкер и почему,
что попало в промпт, что решили gates — без хранения текста документов.

**Один сборщик.** `BenchmarkEvidence` превращается в общий сборщик трассы, который в проде
включён всегда. Benchmark — флаг режима сборщика: обход кэша и текст фрагментов для оценщика.
`lookup`/`store` кэша смотрят на флаг режима, а не на наличие сборщика.
Характеризационный тест: benchmark-трасса до и после изменения совпадает.

**Содержимое трассы (schema_version=1).**
- попытки (`attempts`): исходный, condensed, sub-queries, refinement retry;
- параметры поиска: `fetch_k`, `rerank_top_n`, веса dense/sparse, `exact_ref_boost`, фильтр
  домена и был ли fallback на корпус;
- стадии `retrieved` → `reranked` → `enriched` → `prompt`: для каждого элемента
  `chunk_id`, `document_id`, `content_hash`, позиция, dense/sparse/RRF/rerank score,
  `citation_id`; **без** `content`/`scoped_content` вне benchmark-режима;
- исключения: `chunk_id`, причина (`ExclusionReason`), стадия;
- gates: relevance/sufficiency — вердикт и `reasoning`, обрезанный до 500 символов
  (это вывод модели по контексту, может цитировать документ — показывается по тем же
  правилам, что текст фрагментов); стадия отказа для `not_found`;
- бюджет промпта: `num_ctx`, токены базы/истории/контекста, сколько документов не влезло;
- финиш генерации: `finish_reason`, был ли промпт отправлен.

**Хранение.** Таблица `chat_log_traces(chat_log_id PK FK → chat_logs ON DELETE CASCADE,
schema_version, data JSONB)` — дополняет журнал, а не заменяет: список журнала остаётся лёгким.
Запись — в той же UoW, что и журнал. Трасса пишется для каждого ответа, без сэмплирования.
Настройки (runtime, `observability`-секция): `trace_enabled` (true),
`chat_trace_retention_days` (~30), `chat_log_retention_days` (~180); очистка — периодическая
задача существующего механизма jobs, трассы удаляются раньше журнала.
Размер трассы ограничен (≤ 64 КБ; при превышении — усечение стадий с пометкой).

**Просмотр текста фрагментов (ACL).**
- `GET /admin/chat-logs/{id}/trace` — трасса без текста.
- `POST /admin/chat-logs/{id}/trace/chunks` с `chunk_id[]` из этой трассы — текст фрагментов.
  Порядок проверок: запись журнала в scope просматривающего (правило CURATOR) →
  `chunk_id` действительно есть в трассе этой записи (нельзя читать произвольные чанки) →
  документ видим **просматривающему** через `get_visibility_conditions()` в режиме listing
  с его `UserContext`. Недоступные — `{"chunk_id": …, "hidden": true}`.
  Удалённые/переиндексированные — `{"missing": true}`; текущий `content_hash` сравнивается
  с сохранённым, расхождение показывается как «фрагмент изменился».
- Тесты (разрешённый и запрещённый сценарии): ADMIN видит `CLIENT_PRIVATE` фрагмент
  в трассе (listing-режим); CURATOR видит трассу подопечного, но не видит фрагмент документа
  вне своего scope; CURATOR не получает трассу чужого пользователя;
  `chunk_id` не из трассы — 404.

**UI.** Вкладка «Трасса» в карточке: таймлайн стадий с длительностями; таблица кандидатов
(позиция в каждой стадии, скоры, причина исключения, попал ли в промпт, процитирован ли);
раскрытие текста по клику; gates с вердиктами.

**Готово, когда.** Трасса пишется для всех исходов, кроме `input_blocked`
(вопрос уже в журнале, трасса ничего не добавляет); захват не меняет ответ и кэш (тест
на одинаковый ответ с трассой и без); overhead записи измерен и указан в PR.

**Тесты.** Новые ACL-тесты выше; `test_retrieval_acl.py`, `test_rag_pipeline.py`,
benchmark-тесты трассы (`test_benchmark_evidence.py`) — без изменений результата.

## Этап C. Реакция пользователя

**Domain.** `domain/chat/feedback.py`:
- `MessageFeedback(message_id, user_id, rating: FeedbackRating(up|down), reasons: frozenset[FeedbackReason],
  comment: str | None, creation_date, update_date)`;
- `FeedbackReason`: `no_answer`, `wrong_fact`, `irrelevant_sources`, `incomplete`,
  `outdated`, `too_long`, `other`; причины допустимы только при `down` (инвариант в сущности);
- комментарий ≤ 1000 символов.
- Репозиторий `MessageFeedbackRepository` (порт в Domain).

**Application.** `application/chat/feedback.py`: `rate`, `clear`.
Проверка: сообщение существует, роль `assistant`, беседа принадлежит текущему пользователю —
иначе 404 (не раскрывать существование). Пользователи kind CLIENT оценивают на тех же
условиях. Upsert по уникальному `(message_id, user_id)`
(конкурентные запросы — `ON CONFLICT DO UPDATE`, тест на гонку двух запросов).
Комментарий проходит PII-redaction (как вопрос в журнале) и `html.escape`.

**API.** `PUT /chat/messages/{message_id}/feedback`, `DELETE …/feedback`; rate limit как у чата.
`MessageResponse` в истории беседы отдаёт `id` и текущую реакцию пользователя.

**UI клиента.** 👍/👎 под ответом ассистента; при 👎 — поповер с причинами и комментарием;
повторный клик снимает реакцию.

**Админка.** В журнале — колонка реакции (через `message_id`), фильтры: оценка
(up/down/нет), причина, есть комментарий. В карточке — причины и комментарий.

**Готово, когда.** Тесты: свой ответ — можно; клиент — свой ответ можно; чужой ответ — 404;
сообщение пользователя (не ассистента) — 404/422; причины при `up` — 422; повторная оценка
обновляет, а не дублирует; CURATOR в журнале видит реакции только своих подопечных.

## Этап D. Админка: разбор, перенос в benchmark, сводка

**Разбор записи.** Таблица `chat_log_reviews(chat_log_id PK, status, note, reviewer_id,
update_date)` — разбор ведётся по записи журнала (ошибки тоже разбирают). `status`:
`new`, `benchmark_candidate`, `in_benchmark`, `content_gap` (нужного документа нет),
`pipeline_issue` (документ есть, ответ плохой), `wont_fix`. Фильтр по статусу;
очередь по умолчанию: «👎 или `not_found`/`error`, статус `new`», сортировка по дате;
отдельная очередь `benchmark_candidate` для ADMIN.

**Перенос в benchmark.** CURATOR не получает `BENCHMARK_MANAGE`: он ставит статус
`benchmark_candidate`. Кнопка «В benchmark» в карточке → `POST /admin/chat-logs/{id}/benchmark-question`
(требует `Capability.BENCHMARK_MANAGE`): создаёт вопрос в наборе `<pack>-main` пакета записи
(`pack_key`; можно выбрать `<pack>-quick`, если он есть) с `question` и `history` (предыдущие
ходы беседы) после PII-redaction, `as_of_date`, `source_hint` из источников,
`is_active=false` до заполнения `expected_answer`/`annotations`; ставит статус `in_benchmark`
и хранит ссылку на вопрос. Повторный перенос — 409.
Форма показывает текст вопроса и истории для правки и предупреждает о персональных данных.
Вопрос остаётся в БД (там же, где журнал), в git не попадает.

**Контекст беседы.** В карточке — предыдущие ходы беседы (не более `history_window`)
в том же правиле scope.

**Сводка.** `GET /admin/chat-logs/stats?date_from&date_to&…` (те же фильтры и scope):
распределение исходов и `error_code`, доля 👎 и причины, p50/p95 латентности и TTFT, токены,
доля cache hit, разрез по дням, пространству, модели и `config_hash` (до/после изменения настроек).
Простая страница с карточками и графиками над таблицей журнала.

**Экспорт.** CSV/JSON по фильтру: поля журнала и реакции, без трасс и текста фрагментов;
ограничение по числу строк.

**Готово, когда.** Полный цикл руками: 👎 в чате → запись в очереди → карточка с трассой →
«В benchmark» → вопрос в наборе. Тесты прав: CURATOR без benchmark-capability
не может переносить, но может поставить `benchmark_candidate`; stats учитывают scope CURATOR.

# Часть II. Измерение качества

## Этап E. Классификация ошибок в benchmark

**Цель.** Для каждого вопроса прогона видна причина неуспеха, а не только средний балл.

**Общий словарь исходов.** Результат вопроса в прогоне хранит `outcome: AnswerOutcome`
вместо строки `completion` (`infrastructure/benchmark/evaluation/answer_generators.py`).

**Правило (Domain, `domain/benchmark/diagnosis.py`, чистая функция по метрикам вопроса):**

| Класс | Условие (пороги — параметры, начальные значения ниже) |
|---|---|
| `retrieval_miss` | `fragment_recall_at_k < 1` (или `retrieval_fact_coverage < 1` без фрагментов) |
| `context_loss` | найдено при поиске, но `context_fragment_recall < fragment_recall_at_k` |
| `generation_error` | контекст полон, но `correctness < 7` или `faithfulness < 7` |
| `false_refusal` | `outcome == not_found`, а у вопроса есть ожидаемые фрагменты |
| `false_answer` | вопрос с корректным отказом (`negative`/`false_premise`), а ответ дан |
| `ok` | остальное |
| `unlabeled` | нет аннотаций для решения |

- Вычисляется при сохранении прогона и пересчитывается для старых прогонов по
  `per_question_results` (без повторного запуска).
- `summary_metrics` получает распределение классов; сравнение двух прогонов показывает
  переходы между классами по вопросам («было `ok` → стало `context_loss`»).
- UI: колонка и фильтр класса в результатах; матрица переходов при сравнении.

**Тесты.** Таблица случаев на каждое условие; пересчёт старого прогона.

## Этап F. Наборы вопросов по пакетам и пороги приёмки

**Хранение.** Все вопросы — в БД. JSON пакетов больше не источник; новый стартовый набор
пакета, если понадобится, загружается вручную существующим импортом
(`POST /admin/benchmark/questions/import`), обратной синхронизации нет.

**Соглашение.** `dataset` = `<pack>-<назначение>`. Одна миграция данных без алиасов
переименовывает существующие наборы в `benchmark_questions` и в истории прогонов
(чтобы `bench:regression` находил baseline): `main` → `belarus_law-main`,
`quick-30` → `belarus_law-quick`, `synthetic-support-v1` → `support-synthetic`,
`synthetic-internal-v1` → `internal-synthetic`; `chunking-*` — по принадлежности пакету.
Офлайн-подмножества `benchmarks/chunking/*.json` переименовываются вместе с ними.

**Устойчивость baseline.** Прогон сохраняет хеш каждого вопроса; `bench:regression`
исключает из сравнения вопросы, изменённые после baseline, и перечисляет их.

**Минимальный состав набора (на пакет):** 40–60 вопросов; ≥ 50% фактические с
`expected_fragments`; ≥ 15% — с несколькими обязательными фактами; ≥ 15% — корректный
отказ (`negative`, `false_premise`); ≥ 10% — с `history` (уточнения в беседе);
для права — с `as_of_date`. Проверка — по экспорту набора (`task benchmark:validate -- <export.json>`)
и SQL-проверкой достижимости фрагментов.

**Источники.** Перенесённые из журнала (этап D) — приоритет: это реальные формулировки;
ручные — для покрытия типов. Для `support` и `internal` сбор начинается сразу после
того, как этап D работает на тестовой инсталляции с реальными документами.

**Пороги приёмки.** Хранятся в БД при наборе: минимумы `fragment_recall_at_k`,
`context_fragment_recall`, `correctness`, максимум доли `false_answer`; правило
«не хуже baseline на величину шума» (σ из этапа G). Задаются в админке, `bench:regression`
читает их из БД. `acceptance.json` пакета остаётся только для офлайн-проверок chunking.

**Готово, когда.** Для каждого существующего пакета есть набор `-main` с порогами,
снят baseline; состав набора проверяется скриптом (доли типов).

## Этап G. Калибровка LLM-судьи и шум

**Человеческая разметка.** Таблица `benchmark_human_labels(run_id, question_id, metric,
score 0–10, labeler_id, note)`; в UI результатов прогона — минимальный экран разметки:
ответ, контекст, эталон, оценки `correctness`/`faithfulness`. Разметить 30–50 ответов на пакет
(смешать хорошие и плохие из этапа E). Калибровка повторяется при каждой смене судьи.

**Метрики согласия** (скрипт/эндпоинт): MAE судья↔человек, Spearman, согласие
по бинаризации `≥ 7` (Cohen κ). Хранить вместе с моделью-судьёй и версией промпта судьи
в `config_json` прогона. Если κ < 0.6 — сначала чинить промпт/модель судьи, не пайплайн.

**Шум.** Команда «замерить шум»: три прогона одной конфигурации подряд → стандартное
отклонение каждой сводной метрики. Изменение значимо, если превышает 2σ. σ сохраняется
в БД при наборе вместе с моделью и версией промпта судьи; если судья сменился,
`bench:regression` считает σ недействительной и предупреждает.

**Готово, когда.** Для каждого `-main` набора есть замер согласия и σ; в `docs/quality/README.md`
перенесено правило значимости.

## Этап H. Гейт регрессий

- **Офлайн (каждый PR, трогающий ingestion/chunking/retrieval, в CI):** `task chunking:report`
  на корпусах всех пакетов + сравнение с сохранённым эталоном; новый
  `task quality:offline-gate` падает при снижении BM25/dense recall сверх допуска.
  Если корпус нельзя держать в CI — обязательный шаг в чек-листе PR с приложенным отчётом.
- **Онлайн (вручную автором, перед слиянием PR, меняющего RAG/промпты/модели):** прогон платный,
  запускается, когда PR готов целиком. `task bench:regression` по `-quick` наборам всех пакетов
  с порогами из этапа F и правилом шума из G; полный `-main` — по решению автора PR.
  Результат (run id, дифф классов из E) — в описание PR.
- **После выкатки:** сводка журнала (этап D) по `config_hash` — сравнить долю 👎,
  `not_found` и латентность до/после за 3–7 дней.

**Готово, когда.** Гейт описан в `docs/quality/README.md` и `docs/development/developer-guide.md`;
офлайн-эталоны лежат в репозитории, онлайн-пороги — в БД.
