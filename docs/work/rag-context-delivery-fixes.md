## B1. Фокус таблицы выбирает не ту строку

**Воспроизведение.** Таблица со строками `1 Заявление`, `2 Справка о доходах`,
`3 Копия паспорта`. Вопрос: «Сколько дней на подачу заявления, если прошло 2 недели?»
`focused_table_content` возвращает только строку `| 2 | Справка о доходах | 5 дней |`.

**Причина.** `row_matches_query` (`table_context.py:77-94`) считает совпадением
первую ячейку (обычно номер строки), если она встречается в вопросе как отдельное слово.
Название ищется буквально, без учёта словоформ («заявления» ≠ «Заявление»), поэтому
единственным совпадением оказывается случайное число. Фокус применяется после
реранка (`rag_postprocess.py:224`, `:309`): реранкер видел всю пачку строк,
а LLM получает одну неверную.

**Исправление.**
1. Числовой ключ строки считать совпадением только при явной привязке в вопросе:
   `поле|строка|графа|позиция|пункт|п.|№` + число (с учётом падежей:
   `пол[еяю]`, `строк[аиеу]`, …). Голое число в вопросе («2 недели», «3 дня»)
   строку не выбирает.
2. Название из второй ячейки сравнивать по стеммированным токенам
   (`infrastructure.bm25.tokenizer.tokenize` из Domain импортировать нельзя;
   либо вынести лёгкую нормализацию в Domain, либо передавать матчер из Infrastructure
   в `focus_table_rows`). Совпадение — все значимые токены названия есть в вопросе.
3. Остальное поведение не меняется: если совпадений не ровно одно, пачка остаётся целой.

**Тесты** (`tests/test_table_context.py`):
- новый: вопрос с посторонним числом («…если прошло 2 недели») не сужает пачку;
- новый: «заявления» находит строку «Заявление»;
- существующие должны остаться зелёными: `Формат поля 23?`,
  `test_field_can_be_selected_by_name_without_number`,
  `test_focused_field_keeps_following_editorial_note_and_exceptions`.

## B2. Иерархия разделов обрезается с конца

**Воспроизведение.** Раздел
`Раздел II … > Глава 5 НАЛОГ НА ДОБАВЛЕННУЮ СТОИМОСТЬ > Статья 31. Ставки налога`:
- заголовок блока в промпте: `… > Глава 5 НАЛОГ НА ДОБАВЛЕННУЮ ...`, статья потеряна
  (`context_rendering.py:256-258`, лимит 80 символов);
- префикс в тексте чанка: `… > Статья 31. Ставки на…` (`text_chunks.py:140-142`,
  `shorten_context` оставляет начало строки).

**Причина.** Обе функции режут строку справа, а самый конкретный уровень — последний.

**Исправление.**
1. Новая чистая функция сокращения пути (например, `shorten_breadcrumb(path, limit)`):
   всегда сохраняет последний уровень, затем добавляет уровни справа налево, пока
   помещаются; пропущенные верхние уровни заменяет на `… > `. Если последний уровень
   сам длиннее лимита — обрезает его хвост (номер статьи остаётся в начале).
2. Использовать её в `build_header` (сразу влияет на промпт, переиндексация не нужна)
   и в `context_prefix` (влияет на новые чанки; для старых нужна переиндексация).
3. Разместить функцию так, чтобы её могли импортировать и ingestion, и rag
   (не нарушая направления зависимостей), без дублирования.

**Тесты:** юнит-тесты функции (короткий путь без изменений; длинный путь сохраняет
`Статья 31`; один очень длинный уровень); проверка `build_header` и `context_prefix`.
Прогнать `tests/test_chunking_edge_cases.py`, `tests/test_chunk_context_persistence.py`.

**Риск.** Изменение префикса меняет `page_content`, а значит `content_hash` новых чанков.
Это ожидаемо при переиндексации; смешанный корпус (старые и новые префиксы) работает,
но дедупликация между ними не сработает до полной переиндексации.

## B3. Порядок чанков внутри документа

**Воспроизведение.** Якорь `chunk_index=5` (score 0.9) и предыдущий сосед
`chunk_index=4` (score 0.81): `select_context` рендерит их в порядке `[5, 4]`,
и текст «ПЕРВАЯ часть» оказывается после «ВТОРАЯ часть».

**Причина.** `group_by_document` (`document_sources.py:19-28`) сохраняет порядок
вставки, а `render_selected_docs` (`context_rendering.py:277-300`) рендерит группу
в порядке отбора. Сортировки по позиции в документе нет.

**Исправление.** В `render_selected_docs` внутри группы сортировать по
`(act_version_id, chunk_index)`, где `chunk_index` есть; элементы без индекса
оставлять в исходном порядке после отсортированных (стабильная сортировка).
Порядок групп (по лучшему score) и нумерацию `citation_id` не менять.

Важно: `render_selected_docs` используется и в подсчёте токенов при отборе,
и в relevance gate / sufficiency, и в benchmark-снимках; изменение затронет их
одинаково, это желаемо.

**Тесты** (`tests/test_context_selection.py`): новый тест на порядок `[4, 5]`;
проверить, что `citation_id` у обоих один и тот же. Прогнать
`tests/test_evidence_scope_regressions.py`, `tests/test_benchmark_answer_regressions.py`.

## B4. Перекрытие соседних чанков дублируется

**Воспроизведение.** Текст, нарезанный `text_document_chunks(…, 550, 200)`:
у `chunk0` и `chunk1` общие 182 символа из 504; при рендере обоих хвост `chunk0`
встречается в контексте дважды.

**Причина.** Перекрытие задаётся при нарезке (`merge_fragments` /
`RecursiveCharacterTextSplitter`), а рендер вставляет `page_content` целиком.

**Исправление** (после B3, так как опирается на порядок):
1. В рендере для пары соседних чанков одной группы
   (`chunk_index` отличается на 1, совпадают `document_id`/`act_version_id`)
   отбрасывать у второго чанка повторяющийся префикс контекста `[Раздел: …]`
   и максимальный префикс тела, совпадающий с суффиксом тела первого
   (порог: не меньше ~30 символов, чтобы не резать случайные совпадения).
2. Сравнивать тела без префикса контекста; префикс вычислять тем же кодом, что
   при нарезке, а не регуляркой по тексту.
3. Подсчёт токенов в `select_context` идёт через рендер, поэтому экономия
   автоматически освободит бюджет под дополнительные чанки.

**Тесты:** два соседних чанка → общий фрагмент в контексте один раз;
несоседние чанки (индексы 3 и 5) не обрезаются; чанки разных редакций не обрезаются.

## B5. Родительский текст повторяется у каждого чанка

**Воспроизведение.** Три пункта одной статьи с общим родителем (вводная часть
статьи, 1070 символов): в отрендеренном контексте родитель встречается 3 раза,
это ~2/3 объёма контекста (3351 символ).

**Причина.** `render_selected_docs` вызывает `content_with_parent_scope` для каждого
чанка отдельно (`context_rendering.py:292`); дедупликация внутри функции есть
только в пределах одного чанка (`domain/rag/evidence/context.py`).

**Исправление.**
1. Добавить в `content_with_parent_scope` необязательный параметр
   «уже показанные scope» (множество нормализованных строк) или отдельную функцию
   для групп. В рендере передавать множество, общее для группы документа: каждый
   родитель выводится один раз — перед первым чанком, которому он нужен
   (порядок из B3 гарантирует, что это первый по документу).
2. Не трогать эмбеддинги, sparse и реранкер: там родитель в каждом чанке —
   осознанный выбор («all search models see full scope», `qdrant_ops.py`).
3. Отдельно проверить, что `scoped_response` / evidence profile и
   `rag_sources` не полагаются на то, что каждый блок контекста самодостаточен.

**Тесты:** три пункта одной статьи → родитель один раз и стоит до первого пункта;
два документа с одинаковым текстом родителя → у каждого документа свой экземпляр
(дедупликация только внутри группы). Прогнать `tests/test_context_selection.py`,
`tests/test_evidence_scope_regressions.py`, `tests/test_chunk_context_persistence.py`.

## B6. Бюджет этапа соседей не совпадает с финальным

**Воспроизведение** (вопрос 52 символа, без истории):

| Режим | `compute_context_budget` (этап соседей) | Финальный бюджет контекста в `build()` |
|-------|------------------------------------------|----------------------------------------|
| narrow | 6292 | 4893 |
| broad  | 12836 | 11546 |

**Причина.** `compute_context_budget` (`domain/rag/retrieval.py`) считает
историю и вопрос как символы/4 и резервирует под системный промпт 3000 символов
(≈750 токенов), фактически действует пол 1500. Реальный базовый промпт по той же
оценке, что применяется в `build()` (`estimate_message_tokens`, байты/3), —
около 2800–2900 токенов. В итоге `enrich_with_neighbors` (`retrieval_pipeline.py:320-334`)
подбирает и запрашивает соседей под бюджет на ~29% больше реального; лишние
отбрасываются уже на финальной упаковке, а якоря выбираются от завышенной половины.

**Исправление.**
1. Один источник правды: функция, которая считает финальный бюджет контекста
   из реального базового промпта (`format_generation_messages` c пустым контекстом,
   с учётом истории, summary и domain addendum) через тот же счётчик, что и `build()`.
2. Вызывать её и для этапа соседей, и в `build()`. Если сборка промпта на этапе
   retrieval тяжела, допустимо передавать в `RetrievalWork` готовое число
   «базовые токены» после первой сборки, но не держать вторую формулу.
3. `ContextBudgetOptions.chars_per_token/reserved_overhead` после этого удалить
   или оставить только как запасной путь с тестом на согласованность.

**Отдельный шаг — сначала замер, потом решение.** `estimate_text_tokens` (байты/3)
для русского текста даёт 1587 «токенов» на фрагмент, где `cl100k_base` даёт 1061,
а `o200k_base` — 581. Модель по умолчанию — `qwen/qwen-2.5-7b-instruct`, её токенизатор
локально недоступен, поэтому коэффициент для неё не подтверждён. Нужно сравнить
оценку `input_tokens` из benchmark-снимков (`capture_prompt(... budget=...)`)
с `usage.prompt_tokens` от OpenRouter на тех же запросах. Если завышение
стабильно > 1.3×, подключить точный счётчик через уже существующий параметр
`token_counter` в `build()` или откалибровать коэффициент. Пока замера нет,
это не баг, а гипотеза.

**Тесты:** тест на равенство бюджетов двух этапов для narrow/broad, с историей
и без; существующие `tests/test_rag_policy_characterization.py`,
`tests/test_table_context.py::test_expansion_respects_context_budget`.

## B7. Точная ссылка на пункт ищет голое число

**Воспроизведение.** `extract_exact_references`:
- «что сказано в пункте 5» → `['5']`
- «пункт 3.2 статьи 15» → `['3.2', 'Статья 15']`
- «подпункт 1.4» → `['1.4']`

**Причина.** Для пунктов, подпунктов и `п./пп.` метка не формируется
(`classification.py:184-194`, в `labels` только статья/глава/раздел/параграф).
Затем `search_substring` разрешает однозначное число в пределах документа
(`chunk_search.py:227-232`), а `build_exact_search_stmt` ищет его по границам слова
где угодно в тексте с `ORDER BY id LIMIT 5` (`chunk_search.py:135-149`).
В итоге в кандидаты попадают первые 5 чанков документа, где встречается «5»
(«5 дней», «статья 5», «в пункте 5 статьи 12»), а не пункт 5. Кроме того,
`1.4` совпадает с началом `1.4.2`.

**Исправление.**
1. Сделать ссылки типизированными: `(kind, number)`, где `kind` —
   существующие unit kinds профиля (`article`, `point`, `subpoint_num`, …),
   без новых строковых констант.
2. Для пунктов и подпунктов искать по структурным метаданным чанка
   (`point_number` / `subpoint_num_number` / `article_number` из
   `CHUNK_CONTEXT_FIELDS`, хранятся в `context_metadata`), с сохранением ACL-условий
   и `as_of_date`. Если метаданных нет (старые чанки) — регулярка, привязанная к началу
   строки: `(^|\n)\s*5[.)]\s` и запрет продолжения `\.\d` для `1.4`.
3. Упорядочивать результаты по `chunk_index`, а не по `id`.
4. Голое число без структурной метки в exact search не отправлять.

**Тесты** (`tests/test_exact_reference_retrieval.py`): «пункт 5» находит чанк
пункта 5 и не возвращает чанк со словами «5 дней»; «подпункт 1.4» не находит
`1.4.2`; разрешённый/запрещённый пользователь по ACL (AGENTS.md: для ACL —
оба сценария); `as_of_date` соблюдается. Прогнать `tests/test_retrieval_acl.py`.

## B8. BM25 не различает составные номера

**Воспроизведение.** `tokenize("пункт 3.2")` → `['пункт', '3', '2']`,
`tokenize("пункт 2.3")` → `['пункт', '2', '3']`, то есть одинаковый мешок токенов.

**Причина.** `_TOKEN_RE = [a-zа-яё0-9]+` (`tokenizer.py:10`) режет по точке.
При наличии структурной ссылки в вопросе `compute_retrieval_params` умножает
вес sparse в 2.5 раза (`exact_ref_sparse_boost`), то есть усиливает сигнал,
который не различает нужный пункт и соседние с переставленными цифрами.

**Исправление.**
1. В токенизаторе дополнительно выдавать составной токен для номеров вида
   `\d+(?:\.\d+)+` (например, `3.2`), сохранив и отдельные цифры для обратной
   совместимости recall.
2. Это меняет sparse-векторы: поднять версию `SPARSE_VECTOR_NAME`
   (`bm25_ru_v1` → `bm25_ru_v2`) и переиндексировать sparse. Проверить, что
   `BM25Index` и Qdrant sparse используют один и тот же токенизатор, чтобы
   соответствие ACL-фильтрации и скоринга (AGENTS.md) не нарушилось.

**Тесты:** юнит-тест токенизатора; тест, что запрос «пункт 3.2» ранжирует чанк
`3.2` выше чанка `2.3`; `tests/test_bm25_acl.py`, `tests/test_retrieval_acl.py`.

## B9. Markdown-таблица без разделителя

**Воспроизведение.** Таблица `| Документ | Срок |\n| Заявление | 10 дней |\n…`
без строки `|---|` → `table_header = '| Документ | Срок |\n| Заявление | 10 дней |'`,
и строка «Заявление» повторяется шапкой в каждой пачке.

**Причина.** `table_document_chunks` (`table_chunks.py:67`) всегда берёт первые
две строки как шапку. DOCX/RTF/PDF идут через `render_table`, который всегда
вставляет разделитель, — там дефекта нет. Затронут только Markdown: `_MD_TABLE_RE`
(`markdown.py:20`) принимает любые строки с `|` как таблицу, не требуя разделителя.

**Исправление.** Считать вторую строку частью шапки, только если она похожа на
разделитель (`^\|?\s*:?-{3,}:?\s*(\|\s*:?-{3,}:?\s*)*\|?$`); иначе шапка — одна строка.
Переиндексация нужна только для .md-документов с такими таблицами.

**Тесты:** таблица с разделителем — без изменений; без разделителя — шапка из
одной строки, строка данных не дублируется. `tests/test_chunking_edge_cases.py`.

## Порядок работ

1. **B1** — изолированный, высокий эффект, без переиндексации.
2. **B3 → B5 → B4** — один модуль рендера; B3 нужен для B4/B5. Делать одной серией,
   после каждого шага прогонять тесты контекста.
3. **B2 (заголовок)** — сразу; **B2 (префикс)** — вместе со следующей переиндексацией.
4. **B6** — объединение бюджетов; затем отдельный замер токенизатора.
5. **B7** — exact search по метаданным.
6. **B8, B9** — вместе, одной переиндексацией (sparse и .md).

Для каждого шага: сначала зафиксировать текущее поведение тестом (baseline),
затем изменение, затем целевые тесты:

```bash
cd server && uv run pytest tests/test_table_context.py tests/test_context_selection.py \
```

## Отклонённые гипотезы

| Гипотеза | Почему не баг |
|----------|----------------|
| Конфликт редакций теряет статью из старой редакции | `with_temporal_filter` (`acl.py:107-147`) оставляет на дату ровно одну редакцию по полуоткрытому интервалу; `resolve_temporal_conflicts` срабатывает только при некорректных пересекающихся интервалах |
| Перекрытие переносит хвост предыдущей статьи (LEGAL) | В проде сплиттер собирается с registry и domain_settings (`composition/infrastructure.py:171`), у legal/decree есть `content_boundaries`, поэтому идёт структурный путь, где статья — атомарная единица |
| `fetch_k=15`, фолбэк домена только при 0 кандидатов | Настройки и задокументированное поведение, а не ошибка кода |
| `condense_enabled=False`, декомпозиция реранжируется по исходному вопросу | Настройки по умолчанию; декомпозиция выключена |
| История конкурирует с документами за бюджет | Явный задокументированный выбор (`fit_base_history`) |
| Дедупликация только по точному хэшу | Дизайн; практическая часть (перекрытие) покрыта B4 |
| Неиспользуемые метаданные (`first_sentence`, `extracted_dates`, shape `content_type`), неиспользуемый `select_final_top_k` | Мёртвый код и шум в payload, на контекст LLM не влияет |
| Секция дважды во входе реранкера, последовательный запрос соседей | Косметика и производительность, не корректность |
| `upsert_point` строит sparse без родителя | Не вызывается в продовом коде |
| Слабый суффиксный стеммер | Ограничение качества, не дефект; отдельная задача при необходимости |
| Повтор родителя в dense/sparse/реранкере | Осознанное решение (`prepare_upload_texts`); исправляется только рендер (B5) |
