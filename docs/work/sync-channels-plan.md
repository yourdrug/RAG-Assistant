# План: каналы синхронизации и сверка с GitHub

Рабочий план реализации [ADR 0004](../adr/0004-sync-channels-pull-reconciliation.md).
Не является источником истины о поведении системы; термины — в [глоссарии](../domain/glossary.md)
(«Канал синхронизации», «Прогон синхронизации», «Опубликованная ревизия»).

Общие правила:

- Каждый этап — отдельная ветка/PR; следующий не начинается, пока предыдущий не принят.
- Перед правкой индексации — baseline целевых тестов и `task chunking:report`.
  Платный онлайн-бенчмарк — только после завершения всего PR, перед ним перезапуск `rag-worker`.
- Изменения ACL/RAG сопровождаются тестами разрешённого и запрещённого сценария;
  сохраняются `test_acl.py`, `test_qdrant_sparse.py`, `test_answer_cache.py`, `test_curator_role.py`,
  `test_retrieval_acl.py`, `test_ingestion_acl_consistency.py`, `test_rag_authoritative_access.py`.
- Пути ниже — от `server/app/`.

## Принятые решения

**Канал.** Связывает хранилище с одним пространством знаний, одной видимостью (любой, включая
`client_private` — владельца-клиента указывает админ) и группой; есть ответственный пользователь.
Хранилище — источник истины. Обработчики: pull-GitHub (в этой работе), pull-S3 (позже),
push с ключом канала (позже, когда появится клиент).

**Идентичность файла GitHub:** пространство + экземпляр GitHub + `repository_id` + ветка + полный путь.
Документом считается любой `*.md` под папкой канала с glob-исключениями; имя — путь в репозитории.
Ограничение `*.md` относится только к GitHub-каналам. Лимит размера файла ~5 МБ.

**Права.**
- Привязать репозиторий и расширить охват канала (папка шире, другая ветка, снятие исключения,
  видимость шире, другая группа/владелец) может только админ. Ответственный сужает охват
  и запускает прогоны.
- При каждом прогоне проверяются текущие права ответственного (активен, допущен к пространству,
  для `internal_group` — в группе) и активность владельца-клиента для `client_private`.
  Нарушение — прогон отклоняется, документы остаются.
- Сужение ACL отнимает доступ у прежней аудитории сразу: проверка по БД и инвалидация кэша,
  не дожидаясь Qdrant.

**Владение файлами.** В пространстве файл принадлежит не больше чем одному каналу; проверка — по
настройкам всех каналов, включая не запускавшиеся. Вложенный канал требует исключения во внешнем.
Файл, заявленный двумя каналами, не публикуется ни одним; уже опубликованный — скрывается
из выдачи, конфликт показывается у обоих каналов. Разные ветки — разные файлы, допустимы
в одном пространстве; ветка видна в источнике ответа.

**Прогон.**
- Один прогон на канал; новый запуск отменяет незавершённый. Повторная доставка вебхука
  (`X-GitHub-Delivery`) уже запущенный прогон не отменяет.
- Ветка разрешается в `commit_sha`; дерево читается для этого коммита полностью (при
  `truncated=true` дочитываются поддеревья); содержимое — по `blob_sha` из дерева.
- Удаление — только после полностью прочитанного снимка. Обрыв обхода, недоступная ветка,
  потеря доступа App — документы сохраняются. Подтверждённо пустая папка — удаляются все.
  Порога на удаление нет.
- Каждая публикация и очистка проверяет актуальное **поколение канала** в момент записи.
  Смена настроек, отвязка и удаление канала начинают новое поколение.
- Ошибка файла не отменяет остальные; прогон получает статус «частично».

**Обновление файла** — единица публикации один файл целиком (см. этап 1). Разбор и нарезка
заново; чанки сопоставляются по вхождениям; вектор переиспользуется при совпадении входа
модели (`embed_text`), позиция/секция/путь обновляются отдельно.

**Переименование.** Однозначная пара «исчез путь / появился путь с тем же blob» — перенос
с сохранением `document_id` и векторов. Неоднозначная — новые документы с переиспользованием
эмбеддингов. Источник ответа хранит ветку, путь и `commit_sha` опубликованной версии и ссылку
на файл в этой ревизии; ссылка видна только тем, кому виден документ.

**Ручные изменения и отвязка.** Правка, замена, переименование и удаление документа канала
запрещены в серверных сценариях. Удаление канала — на выбор: удалить документы (по умолчанию)
или отвязать; отвязанный документ сохраняет `document_id` и ACL, становится ручным и выходит
из очистки канала. Пространство канала сменить нельзя.

## Этап 1. Опубликованная ревизия документа (ядро индексации)

**Цель.** Любая переобработка (reprocess, reindex, будущая синхронизация) не убирает документ
из поиска: до полной индексации новой версии поиск и цитаты используют прежнюю.

**Сейчас.** `application/indexing/pipeline.py:251` заменяет строки чанков в Postgres и ставит
в outbox отдельные `DELETE_CHUNKS` и `UPSERT_CHUNKS`; выдача гидрируется из БД, поэтому прежние
точки Qdrant сразу ссылаются на удалённые чанки.

**Что меняется.**
- Чанки и узлы документа получают ревизию; у документа — указатель опубликованной ревизии.
- Новая ревизия пишется скрыто → `UPSERT_CHUNKS` новой ревизии → по завершении outbox
  (`infrastructure/repositories/vector/outbox_dispatcher.py:137`) одна транзакция переключает
  опубликованную ревизию, инвалидирует кэш и ставит удаление чанков старой ревизии.
- Поиск (dense, sparse, гидрация, provision-probe, источники) видит только опубликованную ревизию;
  точки неопубликованной ревизии отбрасываются при гидрации.
- Ошибка индексации оставляет прежнюю ревизию опубликованной, документ помечается ошибкой
  обновления, а не `failed` с пустым поиском.

**Проверки.** Документ ищется во время переобработки; сбой эмбеддинга после записи чанков не
убирает прежнюю версию; после переключения старые точки удалены, кэш промахивается;
ACL-проверка при отставании Qdrant (`test_rag_authoritative_access.py`) не ослабла.

## Этап 2. Инкрементальная переиндексация документа

**Цель.** Правка 50 строк в файле на миллион строк пересчитывает только затронутые чанки
и заметки.

**Что меняется.**
- Сопоставление новых чанков со старыми по вхождениям (повторяющиеся абзацы — отдельно),
  переиспользование dense- и sparse-векторов при совпадающем `embed_text`.
- Ключ контекстной заметки — хеш фактических входов промпта: заголовок, секция, текст,
  оба соседа (`application/indexing/contextualization.py:40`,
  `infrastructure/ml/ingestion/llm_contextualizer.py:116`) вместо хеша всего документа.
  Соседи по-прежнему берутся через границу секции, поэтому их текст входит в ключ.
- Переиспользование работает на общем пути переобработки, не только для каналов.

**Проверки.** Правка одного раздела: число вызовов эмбеддинга и LLM-заметок пропорционально
правке; перенос абзаца под другой заголовок пересчитывает его вектор; результаты поиска
совпадают с полной переиндексацией.

## Этап 3. Канал синхронизации: модель и хранение

**Что меняется.**
- Domain: `SyncChannel` (хранилище, пространство, папка, glob-исключения, ветка, видимость,
  группа/владелец, ответственный, поколение), `SyncRun` (статусы, `commit_sha`, итоги по файлам),
  правила владения файлами и конфликтов, правило «расширение охвата — только админ».
- Привязка документа к каналу и ключу файла, ревизия хранилища опубликованной версии (`blob_sha`, `commit_sha`).
- Запрет ручных изменений документов канала в сценариях `application/documents/` (правка чанков,
  замена, переименование, удаление); отвязка с сохранением `document_id` и ACL.
- Защита S3: очистка префикса (`application/ingestion/sync.py:288`) и `--reset`
  (`composition/cli/commands/ingest.py:65`) не трогают документы каналов.
- Миграция БД, репозитории, UoW.

**Проверки.** Расширение охвата не-админом запрещено, сужение ответственным разрешено;
пересекающиеся каналы в одном пространстве отклоняются, в разных — разрешены; ручная правка
документа канала запрещена, после отвязки разрешена; CLI-очистка не удаляет документ канала.

## Этап 4. Чтение GitHub

**Что меняется.**
- Порт чтения хранилища в Application; адаптер GitHub App в Infrastructure: JWT App →
  installation token, разрешение ветки в коммит, дерево коммита с дочиткой при `truncated`,
  blob по sha, лимит размера, таймауты и ретраи.
- Адрес API — статическая конфигурация (github.com локально, GHES в контуре), включён
  в allowlist по образцу `endpoint_policy.py`. ID App, приватный ключ и секрет вебхука — только
  в env; в API и логи не попадают.

**Проверки.** Неполный обход и потеря доступа дают ошибку снимка, а не пустое дерево;
адрес вне allowlist отклоняется; секреты отсутствуют в ответах и логах.

## Этап 5. Прогон сверки

**Что меняется.**
- Сервис прогона: проверка прав ответственного → снимок коммита → разница с опубликованными
  ревизиями (новые, изменённые, переименованные, удалённые, конфликтные) → публикация файлов
  через этапы 1–2 → удаление после полного снимка.
- Fencing по поколению канала на каждой записи; один прогон на канал; отмена устаревшего.
- Транзакции не охватывают HTTP к GitHub и вызовы эмбеддингов/LLM.
- Выполнение в worker как фоновая задача.

**Проверки.** Конкурентные прогоны A/B: A после отмены ничего не публикует и не удаляет;
ошибочный файл повторяется следующим прогоном при том же коммите; однозначное
переименование сохраняет `document_id`; конфликт скрывает опубликованный файл у обоих каналов;
пустая папка в полном снимке удаляет документы, оборванный снимок — нет.

## Этап 6. Запуск прогонов

**Что меняется.**
- Эндпоинт вебхука App: проверка `X-Hub-Signature-256`, из тела — только экземпляр,
  `repository_id` и ветка; дедупликация по `X-GitHub-Delivery`; быстрый ответ, прогон в фоне.
- Периодическая сверка всех каналов; кнопка «синхронизировать сейчас».

**Проверки.** Неподписанный и неверно подписанный вебхук отклоняется; повторная доставка
не перезапускает прогон; push в неотслеживаемую ветку игнорируется.

## Этап 7. API, UI и источники ответа

**Что меняется.**
- API каналов: создание и изменение охвата (админ), сужение и запуск (ответственный),
  удаление с выбором «удалить/отвязать», история прогонов, ошибки и конфликты по файлам.
- Клиент: экран каналов; у документов канала — пометка «управляется каналом X» вместо
  кнопок редактирования.
- Источник ответа: ветка, путь, `commit_sha`, ссылка на файл в ревизии
  (`infrastructure/ml/rag/rag_sources.py:137`), только при доступе к документу.

**Проверки.** Контракты API, права на каждом эндпоинте (разрешено/запрещено), ссылка
не выдаётся без доступа к документу, старый ответ после переименования открывает
процитированную ревизию.

## Вне этой работы

- Перевод pull-S3 на каналы.
- Push-протокол с ключом канала.
- Самостоятельная привязка репозитория внутренним пользователем через OAuth GitHub.
