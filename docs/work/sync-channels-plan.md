# План: каналы синхронизации и сверка с GitHub

Рабочий план реализации [ADR 0004](../adr/0004-sync-channels-pull-reconciliation.md).
Не является источником истины о поведении системы; термины — в [глоссарии](../domain/glossary.md)
(«Канал синхронизации», «Прогон синхронизации», «Опубликованная ревизия»).

Общие правила:

- Вся работа — одна ветка и один PR; этапы — порядок реализации и коммитов внутри неё.
- Перед правкой индексации — baseline целевых тестов и `task chunking:report`.
  Платный онлайн-бенчмарк — только после завершения всего PR, перед ним перезапуск `rag-worker`.
- Изменения ACL/RAG сопровождаются тестами разрешённого и запрещённого сценария;
  сохраняются `test_acl.py`, `test_qdrant_sparse.py`, `test_answer_cache.py`, `test_curator_role.py`,
  `test_retrieval_acl.py`, `test_ingestion_acl_consistency.py`, `test_rag_authoritative_access.py`.
- Пути ниже — от `server/app/`.

## Принятые решения

**Канал.** Связывает хранилище с одним пространством знаний, одной видимостью (любой, включая
`client_private` — владельца-клиента указывает админ) и группой; есть ответственный пользователь.
Хранилище — источник истины. Обработчик хранилища выбирается при создании канала
(паттерн «Стратегия», см. «Обработчики хранилища»): pull-GitHub (в этой работе), pull-S3
(этап 8), push с ключом канала (позже, когда появится клиент). Сверка, публикация, удаление,
права и `.ragignore` общие для всех обработчиков.

**Идентичность файла GitHub:** пространство + экземпляр GitHub + `repository_id` + ветка + полный путь.
Документом считается любой `*.md` под папкой канала, не исключённый настройками канала
и `.ragignore`; имя — путь в репозитории.
Ограничение `*.md` относится только к GitHub-каналам. Лимит размера файла ~5 МБ.

**Обработчики хранилища (Стратегия).** Канал хранит `storage_kind` и типизированные
настройки хранилища; всё, что зависит от хранилища, спрятано за одним портом снимка
(`StorageSnapshotSource` в `application/sync/ports.py`), реализации — в Infrastructure,
выбор по `storage_kind` — реестром в Composition. Сервис прогона знает только порт.

| Что | Общее ядро (Application/Domain) | Обработчик (Infrastructure) |
|---|---|---|
| Ревизия хранилища | сравнение, хранение в опубликованной ревизии | GitHub: `commit_sha`; S3: метка снимка листинга |
| Список файлов | полнота снимка, удаление, конфликты, `.ragignore` | обход дерева/листинг, флаг полноты |
| Версия файла | обнаружение изменений и переименований | GitHub: `blob_sha`; S3: `sha256` содержимого (ETag multipart не хеш) |
| Содержимое | разбор, нарезка, публикация (этапы 1–2) | чтение blob/объекта с лимитом размера |
| Допустимые файлы | — | GitHub: `*.md`; S3: поддерживаемые расширения `file_storage` |
| Ссылка в источнике | выдача только при доступе | GitHub: файл в коммите; S3: нет внешней ссылки |
| Запуск | один прогон на канал, отмена, периодическая сверка | GitHub: вебхук App; S3: только периодически/вручную |

Push-обработчик реализует тот же порт поверх присланного манифеста, а не отдельную сверку.
Новый тип хранилища = новая реализация порта + секция настроек + запись в реестре; ядро не меняется.

**`.ragignore`.** Файл исключений в синтаксисе `.gitignore` (комментарии, `!`, `/`, `**`, правила
каталогов), разбор — `pathspec` (`gitwildmatch`), явная зависимость. Ищется в папке канала и во всех
вложенных папках снимка; правило вложенного файла действует относительно своей папки, как в git.
Общий для всех обработчиков: в GitHub — файл в репозитории, в S3 — объект `<prefix>/.ragignore`.
- Читается из того же снимка, что и документы (тот же `commit_sha`/листинг); сам не индексируется.
- `.ragignore` только сужает охват, одобренный админом: итоговое исключение = исключения канала ∪
  `.ragignore`. `!` в `.ragignore` не отменяет исключение канала. Поэтому его правку владельцами
  репозитория без админа допускаем: файлы, вернувшиеся после удаления строки, лежат в уже одобренной папке.
- Владение файлами и конфликты каналов считаются только по настройкам каналов, без `.ragignore`:
  его содержимое меняется независимо и до прогона неизвестно. Вложенный канал по-прежнему требует
  исключения в настройках внешнего.
- Файл, ставший игнорируемым, удаляется из канала после полного снимка, как исчезнувший.
- Не удалось прочитать или разобрать любой `.ragignore` снимка — снимок неполный: прогон ничего
  не публикует и не удаляет, ошибка с путём файла видна у канала. Публиковать без исключений нельзя —
  так в индекс попадёт то, что владелец скрыл. Лимит размера `.ragignore` — 64 КБ.
- Действующие правила (канала и `.ragignore` с путём источника) и число исключённых файлов
  сохраняются в итогах прогона.

**Права.**
- Привязать репозиторий и расширить охват канала (папка шире, другая ветка, снятие исключения,
  видимость шире, другая группа/владелец) может только админ. Ответственный сужает охват
  и запускает прогоны.
- При каждом прогоне проверяются текущие права ответственного (активен, допущен к пространству,
  для `internal_group` — в группе) и активность владельца-клиента для `client_private`.
  Нарушение — прогон отклоняется, документы остаются.
- Сужение ACL отнимает доступ у прежней аудитории сразу: проверка по БД и инвалидация кэша,
  не дожидаясь Qdrant.

**Владение файлами.** В пространстве файл принадлежит не больше чем одному каналу; проверка — по
настройкам всех каналов, включая не запускавшиеся. Вложенный канал требует исключения во внешнем.
Файл, заявленный двумя каналами, не публикуется ни одним; уже опубликованный — скрывается
из выдачи, конфликт показывается у обоих каналов. Разные ветки — разные файлы, допустимы
в одном пространстве; ветка видна в источнике ответа.

**Прогон.**
- Один прогон на канал; новый запуск отменяет незавершённый. Повторная доставка вебхука
  (`X-GitHub-Delivery`) уже запущенный прогон не отменяет.
- Ветка разрешается в `commit_sha`; дерево читается для этого коммита полностью (при
  `truncated=true` дочитываются поддеревья); содержимое — по `blob_sha` из дерева.
- Удаление — только после полностью прочитанного снимка. Обрыв обхода, недоступная ветка,
  потеря доступа App — документы сохраняются. Подтверждённо пустая папка — удаляются все.
  Порога на удаление нет.
- Каждая публикация и очистка проверяет актуальное **поколение канала** в момент записи.
  Смена настроек, отвязка и удаление канала начинают новое поколение.
- Ошибка файла не отменяет остальные; прогон получает статус «частично».

**Обновление файла** — единица публикации один файл целиком (см. этап 1). Разбор и нарезка
заново; чанки сопоставляются по вхождениям; вектор переиспользуется при совпадении входа
модели (`embed_text`), позиция/секция/путь обновляются отдельно.

**Переименование.** Однозначная пара «исчез путь / появился путь с тем же blob» — перенос
с сохранением `document_id` и векторов. Неоднозначная — новые документы с переиспользованием
эмбеддингов. Источник ответа хранит ветку, путь и `commit_sha` опубликованной версии и ссылку
на файл в этой ревизии; ссылка видна только тем, кому виден документ.

**Ручные изменения и отвязка.** Правка, замена, переименование и удаление документа канала
запрещены в серверных сценариях. Удаление канала — на выбор: удалить документы (по умолчанию)
или отвязать; отвязанный документ сохраняет `document_id` и ACL, становится ручным и выходит
из очистки канала. Пространство канала сменить нельзя.

## Этап 1. Опубликованная ревизия документа (ядро индексации) — реализовано

**Цель.** Любая переобработка (reprocess, reindex, будущая синхронизация) не убирает документ
из поиска: до полной индексации новой версии поиск и цитаты используют прежнюю.

**Как устроено** (`domain/knowledge/revision.py`, миграция `0011`).
- Документ без опубликованных чанков пишется сразу в `chunks`, как раньше. Иначе новые чанки
  становятся скрытой ревизией: `chunk_staging` (id из той же последовательности, что `chunks`)
  и `document_staged_revisions` (токен ревизии и её узлы). `chunks` по-прежнему содержит только
  опубликованную ревизию, поэтому SQL-чтения не менялись.
- `UPSERT_CHUNKS` скрытой ревизии несёт её токен; диспетчер читает строки из `chunk_staging`
  и пишет точки с `metadata.staged=true`. `build_qdrant_filter()` всегда исключает такие точки,
  поэтому их не видят dense, sparse и scroll-поиск ни для одной роли.
- После загрузки всех точек одна транзакция (под блокировкой строки документа, с проверкой
  токена) переносит ревизию в `chunks` и `document_nodes` и ставит `PUBLISH_REVISION`:
  раскрыть новые точки, затем удалить заменённые. Кэш ответов инвалидируется по документу.
- Новая переобработка отменяет неопубликованную ревизию (её точки удаляются); устаревший
  токен не публикуется.
- Dead letter загрузки скрытой ревизии: ревизия удаляется, документ возвращается в `done`
  с предупреждением, поиск остаётся на прежней версии.
- Смена ACL при переобработке не ждёт публикации: чанки заменяются сразу, иначе
  `chunks.visibility` прежней ревизии расширял бы доступ в SQL-поиске.
- Ручная правка и добавление чанков запрещены, пока у документа есть скрытая ревизия.
- Переименование и pack-метаданные обновляют и скрытую ревизию. Валидация корпуса
  пропускает скрытые точки.

**Проверки.** `test_published_revision.py`, `integration/test_published_revision_postgres.py`;
обновлены сценарии переиндексации (`test_ingestion_acl_consistency.py`,
`test_ingestion_outbox_status.py`, `test_reingestion_consistency.py`).

## Этап 2. Инкрементальная переиндексация документа — реализовано

**Цель.** Правка 50 строк в файле на миллион строк пересчитывает только затронутые чанки
и заметки.

**Как устроено.**
- При записи скрытой ревизии каждый новый чанк сопоставляется с опубликованным по входу
  dense-модели (`embed_text`, иначе текст), повторы — по порядку вхождения
  (`match_reusable_chunks`). Подсказка `reuse_point_id` уходит в outbox.
- При загрузке dense-вектор берётся из старой точки, только если её `embed_hash` и
  `embedding_model` совпадают с новыми; иначе чанк эмбеддится заново. Sparse BM25 всегда
  считается локально из текста чанка (дёшево и не зависит от старой точки).
- Ключ заметки контекстуализации — хеш входов промпта: заголовок, секция, текст и оба соседа
  (`note_input_key`). Правка далеко от чанка сохраняет его заметку.
- Работает на общем пути переобработки, не только для каналов.
- Точки, записанные до этой работы, не содержат `embed_hash`: первая переобработка такого
  документа эмбеддит его целиком; заметки с прежним ключом пересчитываются один раз.

**Проверки.** `test_published_revision.py` (одна правка из трёх — один вызов эмбеддинга,
другая модель — без переиспользования), `test_chunk_contextualization.py` (ключ заметки).

## Этап 3. Канал синхронизации: модель и хранение — реализовано

**Как устроено.**
- `domain/sync/`: `SyncChannel` (`GitHubLocation`: экземпляр, `repository_id`, ветка; папка,
  исключения, `ChannelAudience`, ответственный, поколение), `SyncRun` (статусы
  queued/running/succeeded/partial/failed/cancelled/rejected, ревизия хранилища, итоги по файлам),
  `ignore.py` (исключения канала и `.ragignore` с семантикой git, `pathspec`), `ownership.py`
  (пересечение каналов по настройкам).
- Расширение охвата — только админ: другое расположение или ветка, папка шире, снятое исключение
  или новое `!`-исключение, **любая** смена аудитории (видимость, владелец, группа) или
  ответственного. Ответственный только сужает папку и добавляет исключения. Любое изменение
  увеличивает поколение.
- Права (`application/sync/rights.py`): ответственный — активный внутренний пользователь,
  допущенный к пространству, для `internal_group` — в группе (админ — без членства);
  владелец `*_private`/`client_public` — активный пользователь нужного вида. Проверяются при
  сохранении канала, этап 5 вызывает ту же функцию перед прогоном.
- `SyncChannelService`: создание и удаление — админ; изменение — админ или ответственный.
  Изменения каналов пространства сериализуются блокировкой строки пространства, поэтому
  конкурентные изменения не создают пересекающиеся каналы. Удаление: удалить документы
  (по умолчанию) или отвязать.
- Документ: `SyncBinding` (канал, путь, `storage_version`, `storage_revision`); уникальность
  (канал, путь); документы канала не занимают слот имени, поэтому ручная загрузка с тем же
  именем не сталкивается с ними и не заменяет их. Канал с привязанными документами удалить
  нельзя (FK), пространство с каналами — тоже.
- Ручные правка/добавление чанков, переименование, удаление и переиндексация документа
  канала запрещены; после отвязки разрешены. CLI-очистка префикса и `ensure_document_rows`
  не трогают документы каналов; `delete_internal_documents` их пропускает.
- Миграция `0012`, репозитории, UoW (`sync_channels`, `sync_runs`), контракты import-linter.

**Проверки.** `test_sync_channels.py`, `integration/test_sync_channels_postgres.py`.

## Этап 4. Порт снимка хранилища и чтение GitHub

**Что меняется.**
- Порт `StorageSnapshotSource` в `application/sync/ports.py`, без деталей GitHub:
  `resolve_revision(channel) → StorageRevision`, `list_entries(channel, revision) → Snapshot`
  (пути, версия файла, размер, флаг полноты), `read(channel, revision, entry) → bytes`,
  `source_link(channel, revision, path) → str | None`. Ошибки — общие типы
  (`SnapshotIncomplete`, `StorageAccessLost`, `RevisionNotFound`).
- Реестр обработчиков в Composition: `storage_kind → StorageSnapshotSource`; неизвестный тип —
  ошибка конфигурации канала, не пустой снимок.
- Адаптер GitHub App в Infrastructure: JWT App →
  installation token, разрешение ветки в коммит, дерево коммита с дочиткой при `truncated`,
  blob по sha, лимит размера, таймауты и ретраи.
- Адрес API — статическая конфигурация (github.com локально, GHES в контуре), включён
  в allowlist по образцу `endpoint_policy.py`. ID App, приватный ключ и секрет вебхука — только
  в env; в API и логи не попадают.

**Проверки.** Контрактный набор тестов порта (фейк + GitHub на записанных ответах), который потом
проходит и S3-обработчик. Неполный обход и потеря доступа дают ошибку снимка, а не пустое дерево;
адрес вне allowlist отклоняется; секреты отсутствуют в ответах и логах.

## Этап 5. Прогон сверки

**Что меняется.**
- Сервис прогона работает только через порт снимка: проверка прав ответственного → снимок
  ревизии → применение исключений канала и `.ragignore` → разница с опубликованными
  ревизиями (новые, изменённые, переименованные, удалённые, конфликтные) → публикация файлов
  через этапы 1–2 → удаление после полного снимка.
- Fencing по поколению канала на каждой записи; один прогон на канал; отмена устаревшего.
- Транзакции не охватывают HTTP к GitHub и вызовы эмбеддингов/LLM.
- Выполнение в worker как фоновая задача.

**Проверки.** Конкурентные прогоны A/B: A после отмены ничего не публикует и не удаляет;
ошибочный файл повторяется следующим прогоном при том же коммите; однозначное
переименование сохраняет `document_id`; конфликт скрывает опубликованный файл у обоих каналов;
пустая папка в полном снимке удаляет документы, оборванный снимок — нет; добавленная строка
`.ragignore` удаляет файл, удалённая — возвращает; нечитаемый `.ragignore` — прогон ничего
не меняет.

## Этап 6. Запуск прогонов

**Что меняется.**
- Эндпоинт вебхука App: проверка `X-Hub-Signature-256`, из тела — только экземпляр,
  `repository_id` и ветка; дедупликация по `X-GitHub-Delivery`; быстрый ответ, прогон в фоне.
- Периодическая сверка всех каналов; кнопка «синхронизировать сейчас».

**Проверки.** Неподписанный и неверно подписанный вебхук отклоняется; повторная доставка
не перезапускает прогон; push в неотслеживаемую ветку игнорируется.

## Этап 7. API, UI и источники ответа

**Что меняется.**
- API каналов: создание и изменение охвата (админ), сужение и запуск (ответственный),
  удаление с выбором «удалить/отвязать», история прогонов, ошибки и конфликты по файлам.
- Клиент: экран каналов; у документов канала — пометка «управляется каналом X» вместо
  кнопок редактирования.
- Источник ответа: ветка, путь, `commit_sha`, ссылка на файл в ревизии
  (`infrastructure/ml/rag/rag_sources.py:137`), только при доступе к документу.

**Проверки.** Контракты API, права на каждом эндпоинте (разрешено/запрещено), ссылка
не выдаётся без доступа к документу, старый ответ после переименования открывает
процитированную ревизию.

## Этап 8. Pull-S3 как обработчик канала

**Цель.** S3 и GitHub — два варианта одного канала; отдельной логики синхронизации S3 не остаётся.

**Сейчас.** CLI-загрузка (`composition/cli/commands/ingest.py`) читает префикс через
`file_storage.list_files` (`infrastructure/storage/file_storage.py:213`, фильтр по расширениям),
синхронизирует через `application/ingestion/batch.py` и чистит исчезнувшие ключи
`delete_missing_sources` (`application/ingestion/sync.py:288`); видимость и группа задаются
аргументами команды, ревизий и прав ответственного нет.

**Что меняется.**
- `S3SnapshotSource` реализует порт этапа 4: листинг префикса с пагинацией (обрыв — неполный
  снимок), версия файла — `sha256` содержимого (кэш по ключу+ETag+размеру, чтобы не скачивать
  неизменённые), ревизия — хеш отсортированного листинга, внешней ссылки нет. Проходит
  контрактный набор тестов порта.
- Настройки канала S3: бакет из статической конфигурации `storage`, префикс в настройках канала;
  привязка префикса и его расширение — только админ, как для репозитория.
- `.ragignore` в префиксе работает без изменений ядра.
- Миграция: существующие документы префикса привязываются к новому каналу по ключу
  с сохранением `document_id`, ACL и векторов (без переиндексации); команда миграции идемпотентна.
- CLI `ingest` для префикса становится «создать/запустить канал»; `--reset` и
  `delete_missing_sources` удаляются вместе с отдельным S3-путём синхронизации, когда все префиксы
  переведены. Разовая загрузка файла без канала остаётся ручным документом.

**Проверки.** Контрактные тесты порта для S3; миграция не меняет `document_id`, ACL и выдачу поиска
(`test_ingestion_acl_consistency.py`, `test_retrieval_acl.py`); удалённый из префикса объект удаляется
только после полного листинга; повторная миграция ничего не меняет.

- Самостоятельная привязка репозитория внутренним пользователем через OAuth GitHub.
