# ADR 0003: пространства знаний и пакеты предметной области

Статус: принято, не реализовано.

## Контекст

Одна инсталляция обслуживает одну предметную область, и эта область — белорусское право:
юридические правила свидетельств выбраны по умолчанию (`RagSection.evidence_profile`),
ядро импортирует их напрямую, а редакции актов (`act_version_id`) встроены в модель чанка
и ранжирование. В той же организации нужны ещё внутренний ресурс и клиентская техподдержка.
Им юридические правила вредят (ложные отказы, ссылки на НПА), видимость не отделяет их
документы от юридических по смыслу, а клиенты разных продуктов должны получать ответы
только по своему продукту. Система ещё не в продакшене, существующие данные не сохраняются.

## Решение

**Три уровня.** Пространство знаний связано ровно с одним пакетом предметной области;
пакет объединяет профили документов, правила свидетельств, правила ответа, язык и
benchmark-наборы. Профиль документа может входить в несколько пакетов (`contract` — общий).
Термины — в [глоссарии](../domain/glossary.md).

**Пакет — код в репозитории** с явным реестром, без entry points. Пакет не зависит от другого
пакета; общее выносится в общую библиотеку профилей. Ядро содержит только нейтральный
`generic`/`general` и работает, включая тесты, без пакета права. Без явного выбора
применяется нейтральный пакет.

**Пространство выбирает документы и правила, но не даёт прав на чтение.** Документ принадлежит
одному пространству; вопрос задаётся в одном пространстве и ищет только по его документам,
отвечая по правилам его пакета. Чтение по-прежнему определяет видимость, поэтому соответствие
`is_in_search_scope()` ⇔ фильтр Qdrant ⇔ BM25 ACL не получает нового измерения: пространство
входит в фильтр поиска и ключ кэша как условие выборки. Пополнять пространство могут только
допущенные к нему группы — проверка живёт в сценарии загрузки. Пакет пространства неизменен.

**Клиенты.** ADMIN назначает клиента в пространство поддержки; клиент пространство не выбирает.
Общие статьи получают новую видимость `client_public`. Статьи другого продукта для клиента
нерелевантны, а не секретны; секретное по-прежнему `CLIENT_PRIVATE`.

**Редакции актов — понятие пакета права.** `act_version_id` и учёт редакций уходят из `Chunk`
и ранжирования ядра в метаданные пакета. Для остальных пространств новая версия документа
заменяет старую существующим механизмом замены. Общую модель версионирования источников
и типизированные фасеты метаданных не вводим до реальной потребности.

Порядок: отвязка ядра от `belarus` → реестр пакетов → вынос редакций из ядра → пространства
→ `client_public` и назначение клиентов → пакеты поддержки и внутреннего ресурса.

## Рассмотренные варианты

- **Инсталляция на область** — отвергнуто: организация одна, а пользователи, группы,
  администрирование, БД, Qdrant и ML-модели в памяти дублировались бы трижды.
- **Области через группы** — отвергнуто: группы описывают людей, а не темы; правила ответа
  остались бы глобальными, а тематическая ошибка стала бы ошибкой доступа.
- **Пакет по профилю найденных документов** — отвергнуто: при документах разных пакетов
  неясно, по чьим правилам отвечать, и шум в поиске не устраняется.
- **Пространство как граница чтения** — отвергнуто: новое измерение ACL во всех хранилищах
  ради организации, где видимость уже решает доступ.
- **Пространство под именем «корпус»** — отвергнуто: «корпус» занят физической коллекцией
  векторного индекса (`CorpusSnapshot`).
- **Отложить вынос редакций** — отвергнуто: новая модель не должна унаследовать юридические поля.

## Последствия

Ошибка в пространстве — ошибка релевантности, а не утечка; `client_public` — изменение ACL
и требует тестов «разрешено/запрещено» для всех ролей во всех хранилищах. Вынос редакций
меняет схему БД, payload Qdrant и BM25 и требует переиндексации и регрессии на юридических
benchmark-наборах. Новый пакет считается готовым, когда проходит собственный benchmark-набор;
изменения ядра проверяются на наборах всех пакетов.
