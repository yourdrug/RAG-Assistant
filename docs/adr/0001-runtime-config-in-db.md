# ADR 0001: runtime-конфигурация в PostgreSQL

Статус: реализовано; решение описано по текущему коду, без реконструкции исторических мотивов.

## Контекст и основания

Приложению нужны параметры запуска соединений и секреты до чтения БД, а также
изменяемые параметры RAG/ML и операций. Эти группы уже разделены в
[реестре ключей](../../server/app/application/runtime/setting_keys.py).
[Декларации dynamic-параметров](../../server/app/application/runtime/dynamic_params.py)
служат общим источником для начальных значений, метаданных и валидации снимка.
Существующие API и listener поддерживают изменение без пересоздания всего приложения.
Это подтверждённые свойства реализации; отдельные исторические причины выбора БД здесь не утверждаются.

## Решение

Bootstrap/deployment-параметры остаются в env, секреты — в защищённом secret env.
Активные runtime-параметры хранятся в PostgreSQL как `ConfigParameter` с глобальной
или доменной областью. На старте добавляются отсутствующие defaults, читается полный
снимок writer-БД, выполняются валидация и подготовка ресурсов, затем процесс применяет снимок.
Активные dynamic-ключи из env отфильтровываются до декодирования настроек.

Сохранение и применение независимы. ConfigService валидирует изменение и сохраняет
значение с уведомлением в транзакции; каждый процесс синхронизирует и применяет
собственный снимок. Статус различает `saved_version`, `applied_version`, `ready` и `error`.
Успешный PUT не доказывает применение всеми API/worker-процессами.

Offline-миграция env сохраняет существующие значения БД, переносит секреты и только
при явном `--trim-env` удаляет dynamic/legacy-ключи из исходного env.
Статические overrides сохраняются: замена старого env шаблоном потеряла бы настройки,
которые не управляются runtime-реестром. Commit БД предшествует замене файлов.

## Последствия

БД обязательна для bootstrap API, worker и ML CLI. Нужно отдельно контролировать
применение каждым процессом, доступность listener и ошибки подготовки ML-ресурсов.
Изменение deployment-параметров требует пересоздания процессов; corpus переключается
согласованной операцией, а изменение идентичности embedding требует отдельной миграции корпуса.
Нет общей транзакции между БД и env-файлами: нужны резервные копии и обработка частичного сбоя.
`config resync` применяет снимок только в собственном CLI-процессе.
