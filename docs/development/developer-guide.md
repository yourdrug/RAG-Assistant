# Руководство разработчика

Документ описывает рабочий цикл разработки RAG Assistant. Для общей схемы слоёв и
интеграций см. [обзор архитектуры](../architecture/overview.md), для терминов —
[глоссарий](../domain/glossary.md), для настройки runtime-параметров —
[руководство по конфигурации](../operations/configuration.md). Примеры внешних запросов
смотрите в [быстром старте API](../api/quickstart.md), процедуры оценки — в
[руководстве по benchmark](../quality/README.md).

## Состав проекта

- `server/app/` — Python 3.12 backend на FastAPI.
- `server/app/domain/` — предметные сущности, правила и интерфейсы.
- `server/app/application/` — сценарии приложения, DTO и порты.
- `server/app/infrastructure/` — PostgreSQL, Qdrant, BM25, Redis/Arq, S3/MinIO,
  парсеры и ML-клиенты.
- `server/app/presentation/` — API, схемы HTTP, обработка ошибок и CLI.
- `server/app/composition/` — сборка инфраструктуры и сервисов в DI-контейнере.
- `server/tests/` — unit- и интеграционные тесты.
- `client/src/` — React/TypeScript интерфейс: `pages/`, `widgets/`, `shared/` и
  `features/`.
- `docs/` — постоянная документация проекта; текущие решения фиксируются в `docs/adr/`.

Зависимости backend направлены от Presentation через Application к Domain;
Infrastructure реализует порты, Composition соединяет конкретные реализации.
Сохраняйте это направление при изменении кода.

## Локальный запуск

Основной сценарий разработки использует Docker Compose для приложения и внешних
сервисов. Нужны Docker с Compose, Task и `uv` для работы с Python-окружением.

```bash
task init
```

Команда создаёт env-файлы и каталоги данных и собирает образы. Заполните
`server/.env.secrets` до запуска стека; секреты не коммитьте. Параметры подключения
и публикации портов находятся в `server/.env`, настройки клиентской сборки — в
`client/.env`. Формат и ограничения настроек описаны в
[конфигурации](../operations/configuration.md).

### Подготовка локальных моделей TEI

Шаблон `server/.env` включает `COMPOSE_PROFILES=tei`, а ML provider по умолчанию —
TEI. До первого запуска подготовьте обе модели: Compose монтирует `data/tei_cache`
в `/data` и ожидает каталоги `bge-m3` и `bge-reranker-v2-m3` с весами, конфигурацией
и токенизатором. `task init` их не скачивает.

Из корня репозитория скачайте модели во временный каталог, затем скопируйте их
в хранилище. Пример использует [Hugging Face CLI](https://huggingface.co/docs/huggingface_hub/en/guides/cli)
через `uvx`; потребуется доступ к Hugging Face и место для моделей и временной копии:

```bash
TEI_DOWNLOAD_DIR=$(mktemp -d /tmp/rag-tei-models.XXXXXX)
uvx --from huggingface_hub hf download BAAI/bge-m3 --local-dir "$TEI_DOWNLOAD_DIR/bge-m3"
uvx --from huggingface_hub hf download BAAI/bge-reranker-v2-m3 --local-dir "$TEI_DOWNLOAD_DIR/bge-reranker-v2-m3"
sudo cp -a "$TEI_DOWNLOAD_DIR/bge-m3" "$TEI_DOWNLOAD_DIR/bge-reranker-v2-m3" data/tei_cache/
sudo ./scripts/operations/data-permissions.sh
```

Команды копирования предназначены для первой установки в пустой `data/tei_cache`.
После проверки моделей временную копию можно удалить. Для воспроизводимой установки
добавьте к каждой команде `hf download` параметр `--revision <commit>` и сохраните
идентификаторы ревизий. Обновление моделей существующего корпуса требует отдельной
миграции; не заменяйте его веса произвольной новой версией.

### Запуск сервисов

Сначала запустите TEI и дождитесь готовности, затем всё приложение. Из корня проекта:

```bash
docker compose --env-file server/.env --env-file server/.env.secrets --env-file client/.env -f docker-compose.yml -f docker-compose.override.yml up -d --wait tei-embed tei-rerank
task up
task pull-model MODEL=qwen2.5:7b
```

Если TEI не проходит health-check, проверьте его логи и содержимое каталогов моделей
до запуска приложения. Для окружения с облачным ML эти шаги TEI пропускаются:
профиль Compose и runtime provider должны соответствовать выбранному окружению.

`task up` запускает Compose-стек; генерация LLM работает через OpenRouter.
Выбор модели и ML-провайдера для приложения задаётся runtime-конфигурацией, а не
самим фактом скачивания. Swagger доступен по `http://localhost:8001/docs`, если
используются стандартные локальные порты. Состояние сервисов можно посмотреть в
`task ps`, логи — в `task logs -- server`.

Первый администратор создаётся при старте backend, если заданы `ADMIN_EMAIL` и
`ADMIN_PASSWORD` в env-конфигурации. Используйте сильный пароль. После запуска
проверить доступность приложения можно по `/health`; `/ready` используется для
проверки готовности с учётом внешних зависимостей.

## Проверка первого запуска

Выполните проверку на небольшом документе без чувствительных данных. Она проверяет
весь путь от загрузки до ответа; один успешный `/ready` этого не подтверждает.

1. Откройте `http://localhost:8001/ready`. Ожидается HTTP `200`.
   При `503` проверьте `/health` и логи зависимостей по
   [инструкции диагностики](../operations/troubleshooting.md).
2. Откройте веб-интерфейс (при стандартных портах — `http://localhost:3001`),
   войдите с заданными `ADMIN_EMAIL` и `ADMIN_PASSWORD`.
   Ожидается открытие чата и доступ к административным разделам.
3. Создайте `startup-check.txt` с текстом:
   «Контрольное правило запуска: заявки принимаются по вторникам до 15:00».
   Загрузите его через **Documents**, выбрав `internal_public` и домен `general`,
   если интерфейс предлагает выбор домена. Сохраните ID созданного документа.
   Ожидается появление записи и переход через обработку к `done`.
   При `failed` или длительном `indexing` проверьте **Admin → Jobs** и диагностику outbox.
4. В **Search** выберите режим вхождения (`icontains`) и найдите
   «Контрольное правило запуска». Ожидается фрагмент из `startup-check.txt`
   с указанным текстом. Пустой результат после `done` требует проверки поиска и ACL.
5. В новом чате задайте вопрос: «Согласно контрольному правилу запуска, в какой день
   и до какого времени принимаются заявки?» Ожидается ответ про вторник и 15:00,
   а среди источников — `startup-check.txt`. Откройте источник и сверьте текст.
   Ответ без нужного источника или с другим сроком означает, что проверка RAG
   не пройдена, даже если HTTP-запрос завершился успешно.
6. Отправьте уточнение в том же диалоге, затем откройте его из истории.
   Ожидается сохранение обоих вопросов и ответов в одном разговоре.

После проверки удалите контрольный документ и дождитесь завершения задания удаления.
Для проверки через HTTP используйте [примеры API](../api/quickstart.md).
Перед эксплуатацией также зафиксируйте
[версии моделей и место хранения весов](../operations/recovery.md#учёт-версий-моделей).

## Рабочие команды

Команды проекта определены в корневом `Taskfile.yml`; полный список — `task --list`.

```bash
task install
task test -- tests/test_some_feature.py
task lint
task fmt
```

- `task install` устанавливает зависимости backend через `uv`.
- `task test` запускает Python unit-тесты. Перед правкой бизнес-логики запускайте
  целевые тесты; интеграционные тесты запускаются отдельно через
  `task test:integration -- tests/<путь>` и требуют внешних сервисов.
- `task lint` проверяет форматирование строк, Ruff, mypy, границы импортов,
  зависимости и неиспользуемый код.
- `task fmt` форматирует backend и применяет безопасные исправления Ruff.

Для frontend установите зависимости в `client/`:

```bash
cd client && npm ci
npm run dev
npm run check
npm test
npm run build
```

Команды npm запускайте из `client/`.
`check` запускает Biome и TypeScript typecheck; `test` выполняет тесты клиента на
Node.js. Не запускайте проверки без причины для всего проекта, если достаточно
целевого набора.

## Где вносить изменения

### Новый сценарий backend

1. Найдите существующий сценарий в `application/` и его интерфейсы в `application/ports/`
   или `domain/`.
2. Бизнес-правила поместите в Domain, координацию операций — в Application.
3. Для внешнего сервиса реализуйте порт в Infrastructure; связывайте реализацию
   в `composition/`, а не внутри бизнес-сервиса.
4. HTTP-вход, авторизацию, валидацию и преобразование ошибок оставьте в
   `presentation/api/`. Маршрут должен делегировать работу сервису приложения.
5. Для записи сохраняйте явные commit/rollback через UoW. Для длительной обработки
   используйте существующую очередь фоновых заданий; не держите транзакцию открытой
   во время вызова LLM или другого внешнего сервиса.
6. Добавьте тесты на правило и целевые ошибки/права доступа.

Маршруты регистрируются в `server/app/main.py`; FastAPI lifespan инициализирует
контейнер, БД, конфигурацию и фоновые компоненты. Новые зависимости добавляйте в
Composition согласно существующим провайдерам.

### Изменение API или frontend

Схемы API находятся в `server/app/presentation/api/schemas/`, маршруты — в
`server/app/presentation/api/routes/`. API-документация генерируется FastAPI из
схем и описаний маршрутов. Внешние пути UI обычно идут через `/api`; при локальном
прямом обращении к backend путь начинается с пути самого маршрута.

В клиенте страницы находятся в `client/src/pages/`, маршруты собраны в
`client/src/App.tsx`, общая навигация — в `client/src/shared/config/nav.ts`, API
клиент и обработка токена — в `client/src/shared/api/` и `client/src/stores/`.
Права проверяйте на backend: скрытие пункта меню не заменяет серверную авторизацию.

### ACL, документы и RAG

При изменении доступа проследите правило от Domain до всех адаптеров и выдачи
источников. Для ACL сохраняйте согласованность
`is_in_search_scope()` ⇔ Qdrant `build_qdrant_filter()` ⇔ BM25
`_doc_matches_acl()`. Проверяйте dense поиск, разрешение BM25-кандидатов и ссылки
на источники. Роль администратора для просмотра списка не означает доступ к любому
документу в RAG-поиске. При изменении retrieval/ingestion запускайте относящиеся к
правке ACL-тесты, включая `test_retrieval_acl.py` и
`test_ingestion_acl_consistency.py`.

Полная таблица видимости и путь распространения UserContext находятся в
[описании ACL](../architecture/access-control.md); порядок этапов и разрешённые места
повторной фильтрации — в [описании RAG pipeline](../architecture/rag-pipeline.md).

### Схема БД и runtime-конфигурация

Изменения схемы БД оформляйте миграцией Alembic. Для создания ревизии используется
`task db:migrate:make -- "описание"`, применение миграций — `task db:migrate`.
Проверьте сгенерированную миграцию вручную: autogenerate не заменяет ревью.

После изменения `server/pyproject.toml` обновите `server/uv.lock` командой
`task lock`. Не добавляйте библиотеку, если нужная функциональность уже доступна в
зависимостях. Значения runtime-конфигурации в БД редактируются через админку; не
подменяйте их случайными env-переменными — см. ADR и
[описание конфигурации](../operations/configuration.md).

## Документация и завершение работы

Обновляйте постоянные документы, когда меняется пользовательское поведение,
инструкция запуска, API-контракт или архитектурное решение. Для принятого решения
с существенными последствиями добавляйте ADR. Перед завершением проверьте diff,
запустите проверки, относящиеся к изменению, и укажите в описании результата,
какие именно команды выполнялись.
