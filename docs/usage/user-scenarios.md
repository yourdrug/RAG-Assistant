# Пользовательские сценарии

Документ описывает основные сценарии интерфейса и границы доступа в RAG Assistant.
Пункты меню зависят от роли, но окончательную проверку прав выполняет backend.
Примеры запросов для интеграции через HTTP API приведены в
[быстром старте API](../api/quickstart.md).

## Роли и тип аккаунта

В системе различаются роль (`admin`, `curator`, `user`) и тип аккаунта
(`internal`, `client`). Роль задаёт набор действий, тип — контекст владения и
доступа к клиентским документам. Фактическая видимость определяется также
владельцем документа, группами и назначениями куратора.

| Кто | Основные возможности интерфейса |
|---|---|
| Пользователь (`user`) | Чат, история своих диалогов, просмотр доступных документов и точный поиск по доступным фрагментам. |
| Куратор (`curator`) | Возможности пользователя, управление документами в разрешённом scope, просмотр админ-разделов, доступных куратору. |
| Администратор (`admin`) | Пользовательские сценарии и полный набор административных разделов: пользователи, группы, ключи API, настройки, загрузка из S3, задания и мониторинг. |
| Клиент (`kind=client`) | Аутентификация API-ключом для интеграций; видит только данные, разрешённые клиенту и его назначениями. В веб-интерфейсе действия также зависят от роли. |

Тип аккаунта `client` сам по себе не расширяет возможности роли. Клиентский ключ
создаёт администратор; секрет ключа показывается при выпуске, поэтому его нужно
сохранить в защищённом хранилище.

## Вход и начало работы

1. Откройте `/login` и войдите по учётным данным.
2. При успешном входе интерфейс сохраняет JWT, получает профиль и открывает чат.
   Просроченный или недействительный токен требует повторного входа.
3. Для выхода откройте действие выхода в боковой панели. Клиент очищает локальное
   состояние и возвращает на страницу входа.

При интеграции через API внутренние учётные записи используют
`Authorization: Bearer <JWT>`. Внешние client-аккаунты могут использовать
`Authorization: Api-Key <ключ>`.

## Задать вопрос и продолжить диалог

1. Откройте **Chat**, введите вопрос и отправьте его.
2. Интерфейс показывает ход ответа и принимает потоковые события сервера: этапы
   обработки, фрагменты текста, затем итоговые метаданные.
3. В завершении отображаются источники, доступные текущему пользователю. Откройте
   источник, чтобы перейти к соответствующему документу/фрагменту.
4. Новый диалог создаётся действием нового чата. Список прошлых диалогов находится
   в панели истории; выбор диалога загружает его сообщения.
5. Если LLM недоступна или сервер занят, поток может завершиться сообщением об
   ошибке. Повторите запрос позже.

Вопросы и ответы сохраняются в истории текущего пользователя. Фильтрация доступа
действует при поиске и формировании источников: наличие документа в административном
списке не гарантирует, что этот документ войдёт в ответ RAG.

## Найти документ или фрагмент

1. Перейдите в **Search** и введите текст для поиска.
2. Результаты ограничены доступными пользователю документами. Точный поиск ищет
   совпадения в текстовых фрагментах; он предназначен, например, для поиска
   известной формулировки, а не для ответа на вопрос естественным языком. Нужно
   ввести не менее трёх символов; доступны режимы ранжированного поиска и поиска
   вхождения.
3. Просмотрите имя документа и подсвеченный фрагмент в выдаче. Для чтения полного
   документа перейдите в **Documents** и откройте его там, если он доступен вам.

Различайте поиск совпадения в тексте и чат: чат использует RAG-конвейер, который
подбирает контекст и формирует ответ с источниками.

## Просмотреть и загрузить документы

На странице **Documents** пользователь видит документы, доступные его текущему
контексту. Из списка можно открыть документ, просмотреть состояние обработки и
доступные действия.

Пользователь с правом управления документами может загрузить файл:

1. Выберите файл и параметры видимости; если применимо, укажите группу или клиента.
2. Подтвердите загрузку. Сервис сохраняет исходный файл и ставит обработку в очередь.
3. Следите за статусом документа. После фоновой обработки и индексации документ
   становится доступен для разрешённых сценариев поиска; при ошибке проверьте
   статус задания или обратитесь к администратору.

Статусы описывают разные этапы обработки:

| Статус | Что происходит |
|---|---|
| `pending` | Запись документа создана, задание ожидает обработки. |
| `processing` | Файл читается, извлекается текст, выполняются классификация и разбиение на чанки. |
| `indexing` | Чанки сохранены, завершается синхронизация векторного индекса. Это может быть нормальным промежуточным состоянием. |
| `done` | Обработка и синхронизация индекса завершились. |
| `failed` | Обработка документа завершилась ошибкой. Причину смотрите в `error_message` и связанном задании в **Jobs**. |

Если документ долго остаётся в `indexing`, администратору следует посмотреть счётчики
`outbox_pending` и `outbox_failed` у документа и проверить логи worker. Наличие ошибок
outbox означает, что нужно разбирать синхронизацию индекса; не меняйте статус документа
вручную. Предупреждения парсера и оценка извлечённого содержимого доступны в карточке
документа, если они были сформированы.

Видимость документа может быть общей для внутреннего корпуса (`internal_public`),
ограниченной группой (`internal_group`), частной для владельца внутри организации
(`internal_private`) или частной для клиента (`client_private`). Выбор видимости
определяет область доступа. Не размещайте в общедоступном разделе данные,
предназначенные конкретному владельцу, группе или клиенту.
Администратор также может запустить удаление документа; удаление выполняется
асинхронным заданием. Удаление принято к исполнению не означает, что оно уже завершено:
проверяйте состояние задания в **Jobs**.

## Администрирование

Администратор открывает **Admin** из основной навигации. Куратор видит только
разделы, разрешённые его роли; административные API дополнительно проверяют права.

Основные задачи администратора:

- **Users** — создать внутреннего пользователя или client-аккаунт, изменить роль,
  включить или деактивировать учётную запись.
- **Groups** — создать группу и назначить в неё пользователей. Членство используется
  для доступа к документам с видимостью `internal_group`.
- **Curators** — назначить пользователей и группы в scope куратора. Доступ к данным
  куратора ограничивается назначениями.
- **API Keys** — выпустить ключ для client-аккаунта, просматривать состояние и
  отзывать ключи. Передавайте сам секрет только клиентской интеграции.
- **Ingest** — запустить обработку файлов из S3-префикса или отдельного файла,
  выбрать домен и параметры видимости, посмотреть реестр индексации. Повторная
  индексация выбранного префикса сохраняет существующие ID и назначения доступа;
  параметры видимости применяются к новым документам.
- **Jobs** — проверять состояние фоновой обработки и диагностировать неудачные
  задания.
- **Settings / Models** — управлять runtime-конфигурацией и параметрами ML. После
  сохранения отдельно проверяйте состояние применения параметров.
- **Documents / Act Versions** — просматривать корпус и управлять документами и
  редакциями в рамках разрешений.
- **Quality / Benchmark** — запускать проверки качества и оценивать изменения
  retrieval/ответов на подготовленном наборе вопросов.
- **Dashboard / Vector DB / Logs / Chat Logs** — наблюдать за компонентами,
  метриками, действиями и журналом запросов согласно доступному scope.

## Статусы сервисов и проблемы

- Если вход завершается `401`, проверьте учётные данные и войдите снова. Для API
  проверьте срок JWT или действительность/отзыв API-ключа.
- Если действие завершается `403`, текущая роль или scope не разрешает операцию;
  попросите администратора проверить роль, группу и назначения.
- Если документ долго остаётся в `processing`/`indexing` или имеет статус ошибки,
  проверьте административный раздел **Jobs** и журнал сервера.
- Если чат недоступен, администратор может проверить `/health`, состояние LLM и
  применённую runtime-конфигурацию.
