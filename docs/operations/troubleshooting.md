# Диагностика инцидентов

Начните с определения времени начала сбоя и затронутой функции. Сопоставляйте
HTTP-проверки, состояние контейнеров и логи за один временной интервал. Не удаляйте
данные вручную и не запускайте `task clean` в production.

## Первичная проверка

Для production Compose:

```bash
source scripts/operations/compose.sh
compose ps
compose logs --tail=200 server worker
```

С клиентского nginx проверьте разные уровни готовности:

```bash
curl --fail-with-body --silent --show-error http://127.0.0.1:3001/api/live
curl --fail-with-body --silent --show-error http://127.0.0.1:3001/api/health
curl --fail-with-body --silent --show-error http://127.0.0.1:3001/api/ready
```

`/api/live` подтверждает, что процесс backend отвечает. `/api/health` показывает
проверки зависимостей и фоновых заданий. `/api/ready` возвращает `503`, если система
не готова обслуживать запросы. При необходимости посмотрите логи `postgres`, `qdrant`,
`redis`, `minio` и выбранного ML-сервиса через тот же `compose logs`.

## Частые ситуации

| Симптом | Что проверить | Следующее действие |
|---|---|---|
| `/ready` отвечает `503`, но `/live` работает | Поля `checks` в `/health`, состояние сервисов через `compose ps`, логи backend и проблемной зависимости. | Устраните отказ конкретной зависимости и повторно проверьте `/ready`; не считайте ответ `/live` подтверждением готовности. |
| Документ долго остаётся в `processing` | Статус и `error_message` документа, соответствующее задание в **Admin → Jobs**, логи worker и Redis. | Сохраните ID документа и задания, время и текст ошибки. Не меняйте статус документа вручную. |
| Документ долго остаётся в `indexing` | Поля `outbox_pending`, `outbox_failed` и `outbox_failed_details` документа; логи worker и Qdrant. | Ненулевой `outbox_pending` указывает на ожидающую синхронизацию. При `outbox_failed` передайте детали оператору индексации; не переиндексируйте корпус целиком без отдельного плана. |
| Очередь фоновых заданий растёт | Сводку `background_jobs` в `/health`, `compose ps`, логи worker и Redis. Для конкретного задания используйте **Admin → Jobs**. | Проверьте, что worker и Redis доступны и нет повторяющейся ошибки обработки. До исправления причины избегайте массового повторного запуска заданий. |
| Чат отвечает ошибкой доступности LLM | `llm_provider` и проверки `/health`, логи backend и выбранного ML-сервиса, состояние применения runtime-конфигурации. | После восстановления провайдера повторите запрос. При `503` соблюдайте `Retry-After`; смену провайдера выполняйте через управляемую конфигурацию. |
| Заканчивается место | `df -h data` и размер каталогов `du -sh data/*`. | Расширьте или освободите место по утверждённой политике хранения. Не удаляйте вручную файлы Postgres, Qdrant, MinIO или Redis. |
| Backup завершился ошибкой | `journalctl -u rag-backup.service`, код завершения и каталог результата; проверьте remote-копию отдельно. | Не считайте один timestamp подтверждением пригодности копии. Проверьте её через `restore-check.sh`; порядок описан в [руководстве восстановления](recovery.md). |

В API просмотр `/admin/jobs` и `/admin/jobs/{job_id}` требует администратора. Поля
документа и диагностика outbox зависят от доступного пользователю scope.
