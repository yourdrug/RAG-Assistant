# Конфигурация

## Источники и bootstrap

| Группа | Где задаётся | Когда применяется |
|---|---|---|
| Bootstrap / deployment | `server/.env` и окружение процесса: соединения PostgreSQL/Redis, S3, CORS, статические ограничения и Docker-параметры. | При запуске; изменённое окружение контейнера требует его пересоздания. |
| Секреты | `server/.env.secrets`: пароли, JWT secret, API-ключи, S3 credentials. | При запуске; файл с правами `0600`. |
| Runtime | PostgreSQL, `ConfigParameter`, глобальный или доменный `domain_key`. | Валидированный снимок применяется процессом; большинство параметров — со следующей операции. |
| Frontend | `client/.env`, в частности `VITE_API_URL`. | При сборке Vite. |

Точный состав групп: [setting_keys.py](../../server/app/application/runtime/setting_keys.py).
Типы и defaults: [config.py](../../server/app/config.py); активный динамический реестр:
[dynamic_params.py](../../server/app/application/runtime/dynamic_params.py).
Реестр включает LLM/ML endpoints и модели, RAG, OCR, ingestion, квоты, retention и corpus.
Некоторые параметры остаются статическими, поэтому название категории не определяет источник.
Секреты не редактируются через runtime API; effective API показывает только их наличие.
Не помещайте credentials в URL динамических endpoints.

Из корня репозитория `task env` создаёт отсутствующие файлы из шаблонов и выставляет
`0600` для secret env, не перезаписывая значения. Перед первым запуском заполните секреты.
Pydantic читает `server/.env`, затем `server/.env.secrets`; окружение процесса имеет
приоритет. Но активные dynamic-ключи отфильтровываются из обоих env-источников ещё до
декодирования: оставленный в старом env параметр не становится runtime override.

[Bootstrap](../../server/app/composition/infrastructure.py) API, worker и ML CLI
добавляет отсутствующие глобальные/доменные defaults и загружает полный снимок из
writer-БД. Подготовка ML-клиентов и валидация должны пройти до применения.
API отдельно создаёт начального администратора при заданных `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
Для legacy env выполните миграцию до запуска нового приложения: уже существующие
строки БД миграция сохраняет, включая defaults от предыдущего запуска.

`COMPOSE_PROFILES=tei` включает локальные Docker-сервисы TEI. `ML_PROVIDER` в БД
выбирает провайдера приложения и не запускает контейнеры. `task pull-model MODEL=...`
только скачивает модель Ollama; её выбор задаётся runtime-конфигурацией.

## Сохранение, применение и диагностика

Админка [settings.tsx](../../client/src/pages/admin/settings.tsx) читает сохранённые
параметры и отдельно опрашивает status/effective каждые 3 секунды.
Все следующие API требуют администратора. В таблице указаны внешние пути через
клиентский nginx с префиксом `/api`; при прямом обращении к FastAPI этот префикс
нужно убрать (например, `/admin/config/status`).

| API | Что показывает или делает |
|---|---|
| `GET /api/admin/config` | Сохранённые редактируемые параметры и метаданные. |
| `PUT /api/admin/config/{key}` | Валидация и сохранение `{"value":"..."}`; для доменного значения — `?domain=legal` или другая зарегистрированная область. |
| `GET /api/admin/config/status` | `saved_version`, `applied_version`, `ready`, `error` текущего API-процесса. |
| `GET /api/admin/config/effective` | Источник, `configured_value`, `applied_value`, область и режим применения каждого параметра. |

Версии — хеши активного снимка, а не последовательные номера изменений.
Успех PUT означает сохранение. Применение подтвердите совпадением версий,
`ready=true`, отсутствием `error` и ожидаемыми effective-значениями.
Режимы: `next_operation`, `next_cron` (retention `job_cleanup_days`), `recreate`
(статические параметры и секреты), `corpus_switch` (Qdrant endpoint/collection).
Статус одного API-процесса не доказывает готовность остальных API и worker.

Изменения распространяются через PostgreSQL `LISTEN/NOTIFY`; listener синхронизирует
полный снимок при уведомлении и переподключении. При расхождении проверьте доступность
writer-БД, подключение listener и логи resync/подготовки ML. Исправьте причину,
дождитесь повторной синхронизации и снова сравните status/effective. Кнопка Refresh
в UI повторяет чтение статуса и не запускает принудительную синхронизацию соседних процессов.

`config resync` выполняет bootstrap и применяет снимок **только внутри своего CLI-процесса**.
Команда не заставляет уже работающие API/worker перечитать БД, требует их инфраструктурных
зависимостей и может добавлять отсутствующие defaults при bootstrap. Это не чистая команда
диагностики и не широковещательный механизм исправления состояния.

Обычный PUT запрещает изменение `qdrant_url`/`collection_name`: используйте согласованный
`POST /api/admin/corpus/switch` с проверкой ожидаемого поколения. Изменение идентичности
embedding требует отдельного workflow миграции корпуса; смена строки настройки не заменяет переиндексацию.

## Offline-миграция legacy env

Ниже команды для локального окружения, установленного через `task install`.
Синтаксис сверён с текущим CLI, включая `config migrate-env --help`.
Во время подготовки документа эти операции не выполнялись.

Предварительные условия:

1. Остановите API, worker, ML CLI и остальных writers конфигурации; PostgreSQL оставьте
   доступным. Убедитесь, что схема БД соответствует текущей версии приложения.
2. Подготовьте bootstrap env/credentials для подключения CLI именно к нужной writer-БД.
   `--env-file` выбирает файл для разбора и изменения, но не перенастраивает подключение
   уже импортированного `config.settings`. Хостовые команды могут требовать своего `DB_HOST`/`DB_PORT`.
3. Сохраните отдельно БД, оба env-файла и перечень нестандартных static overrides.
   Закройте доступ к копиям: они содержат секреты. Не публикуйте их в Git или выводе ревью.
4. Файлы не должны быть symlink; каталог должен быть доступен для создания backup и
   атомарной замены. Соседний secret-файл определяется именем: `.env` → `.env.secrets`.
5. Разрешите конфликты секретов между env, secret env и окружением процесса. Нужны
   `DB_PASSWORD`, `REDIS_PASSWORD`, `JWT_SECRET_KEY`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`;
   выбранный облачный provider требует соответствующий API-ключ. S3-параметры старых
   строк БД должны согласовываться с deployment-конфигурацией, иначе миграция блокируется.

Резервирование до запуска: сделайте проверенный дамп writer-БД принятым способом и
защищённые копии `server/.env` и `server/.env.secrets` (если второй файл существует).
Для штатного Compose можно получить логический дамп из корня проекта:

```bash
mkdir -p backups/config-migration
chmod 700 backups/config-migration
(umask 077; docker compose --env-file server/.env --env-file server/.env.secrets exec -T postgres sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/config-migration/before.dump)
cp -p server/.env backups/config-migration/before.env
# Если secret env уже существует:
cp -p server/.env.secrets backups/config-migration/before.env.secrets
chmod 600 backups/config-migration/*
```

Проверьте успешный код возврата `pg_dump` и пригодность дампа к восстановлению;
пустой или непроверенный файл не является резервной копией. При внешней БД используйте
её writer и соответствующий способ резервирования. Имена выше предназначены для одного
окна обслуживания: для следующего выберите новый каталог, не перезаписывая предыдущий backup.

Из корня репозитория перейдите в `server/app` и выполните сначала dry run:

```bash
cd server/app
../.venv/bin/python -m composition.cli config migrate-env --env-file ../.env --trim-env
```

Без `--apply` нет записей в БД и env. Dry run подключается к БД, проверяет значения и
выводит действия по именам ключей без значений. Сверьте `Insert`, `Preserve DB`, перенос
секретов, удаление старых S3-строк и сокращение env. Существующее значение БД побеждает
legacy env; если это неожиданно, не продолжайте до разбора расхождения.

Применение из того же каталога и с тем же окружением:

```bash
../.venv/bin/python -m composition.cli config migrate-env --env-file ../.env --trim-env --apply
```

Миграция не инициализирует ML-клиенты. Она валидирует импортируемые значения, но не
заменяет полную проверку runtime-снимка и готовности внешних сервисов при старте.
Она создаёт защищённые соседние `.backup-*` файлы для существующих env-файлов, добавляет
только отсутствующие пары `(key, domain_key)` и удаляет согласованные legacy S3-строки БД.
После commit сначала устанавливается secret env, затем основной env. Файлы заменяются
атомарно по отдельности; конкурентное изменение файла блокирует его замену.

`--trim-env` удаляет перенесённые dynamic-ключи, старые общие HTTP pool-ключи и
`EMBED_MODEL`/`RERANK_MODEL`/`RERANK_DEVICE`. Static overrides и неизвестные ключи сохраняются.
Без `--trim-env` dynamic-ключи остаются в env; перенос секретов выполняется и в этом режиме.
Legacy HTTP pool-параметры преобразуются в раздельные embedding/rerank limits;
конфликт старых и новых явных значений блокирует операцию. Если `COMPOSE_PROFILES` не задан,
legacy TEI provider может добавить профиль `tei`; явно заданный профиль сохраняется.

После успеха сверяйте файлы локально без публикации секретов: static overrides должны
сохраниться, секреты — находиться в secret env с `0600`. Пересоздайте процессы с новым
окружением, затем проверьте status/effective каждого нужного runtime и готовность приложения.

## Частичный сбой и восстановление

Между commit БД и заменой двух файлов нет общей транзакции.

- Ошибка до commit: транзакция откатывается; env ещё не заменены. Backup мог уже появиться.
- Ошибка после commit: строки БД уже сохранены. Secret env мог обновиться, а основной env
  остаться старым. Сам факт ненулевого exit code не означает откат БД.
- При конфликте конкурентной записи INSERT завершает транзакцию ошибкой вместо перезаписи
  чужого значения; при изменении файла нужно заново сверить dry run.

Оставьте writers остановленными, сохраните backup и проверьте фактическое состояние БД
и обоих файлов. Исправьте причину ошибки и повторите dry run, затем применение:
существующие строки БД сохраняются, одинаковые секреты в обоих файлах допустимы.
Не заменяйте env шаблоном и не пытайтесь исправить сбой массовым удалением строк БД.

Если нужен полный откат, в том же окне обслуживания восстановите writer-БД из проверенного
дампа и **оба** env-файла из копий одного момента, сохранив исходное наличие/отсутствие
secret env и его права. Не восстанавливайте только env: dynamic-ключи всё равно читаются
из БД. Восстановление БД может затереть более поздние записи, поэтому сначала убедитесь,
что после backup не было чужих изменений. Возврат к старой версии приложения требует
также совместимой схемы; эта инструкция не выполняет downgrade схемы автоматически.
После восстановления запустите согласованную версию и снова проверьте готовность.
