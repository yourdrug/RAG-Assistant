# Резервное копирование и восстановление

Инструкция описывает штатные скрипты cold backup для локальных Compose-хранилищ.
Сценарии с внешней PostgreSQL или S3 требуют отдельной копии этих сервисов у
провайдера. Для миграции только runtime-настроек см. отдельный раздел
[частичный сбой и восстановление](configuration.md#частичный-сбой-и-восстановление).

## Что попадает в резервную копию

`scripts/operations/backup.sh` создаёт каталог с UTC-меткой времени, содержащий:

- `postgres.dump` — логический PostgreSQL dump в формате custom;
- `data.tar.gz` — остановленные каталоги `postgres`, `qdrant_storage`, `minio` и
  `redis`, снятые согласованно;
- `images.txt` и, если существует `.deploy/current.env`, `release.env` — сведения
  об образах и текущей версии;
- `SHA256SUMS` — контрольные суммы dump, архива данных и списка образов.

В копию не входят `server/.env`, `server/.env.secrets`, `client/.env`,
`.operations.env`, конфигурационные файлы в `data/db/postgres/`, TLS-сертификаты,
код приложения и веса Ollama/кэш TEI. Храните нужные для запуска версии этих файлов
и сертификатов отдельно, в защищённом и доступном при аварии месте. Данные MinIO,
PostgreSQL и векторы содержат пользовательский корпус; скрипт не шифрует архив.

Снимок локальных контейнеров требует окна обслуживания. Для внешнего PostgreSQL,
S3 или внешнего Qdrant архив из этого скрипта не является полной резервной копией.

## Учёт версий моделей

До первой резервной копии и после каждого согласованного изменения моделей заведите
паспорт окружения в защищённом хранилище за пределами хоста. Связывайте его с конкретным
каталогом backup по UTC-метке и имени. Это отдельный ручной документ: `backup.sh`
сохраняет `release.env` и `images.txt`, но не создаёт паспорт моделей и не копирует веса.

| Что записать | Откуда взять / что сохранить |
|---|---|
| Release приложения и образы | Версия приложения, `release.env`, `images.txt`; для точного восстановления — digest образов API/worker, TEI и Ollama. |
| Применённая runtime-конфигурация | Значения из admin status/effective, `applied_version`, доменные overrides. Укажите `ml_provider`, `llm_provider`, выбранные модели, `embedding_revision`, `embed_dim` и `collection_name`. |
| Локальные TEI-модели | Repo ID и точный Hugging Face commit каждой модели, параметры запуска TEI, отдельная копия каталогов `data/tei_cache/bge-m3` и `data/tei_cache/bge-reranker-v2-m3` с весами, конфигурацией и токенизаторами. |
| Ollama | Имя и tag используемой модели, её ID/digest, отдельная копия `data/ollama_models`; список установленных моделей можно посмотреть через `compose exec ollama ollama list`. |
| Облачные модели | Provider, точные ID embedding/reranker/LLM и доступная провайдеру версия. Отметьте, если провайдер не гарантирует неизменность модели по ID. |
| Хранилище весов | Достижимый при потере хоста адрес отдельной копии, её контрольные суммы, дата проверки и порядок получения доступа. Секреты храните отдельно от паспорта. |

`embedding_revision` — идентификатор версии embedding в приложении. Он сам по себе
не фиксирует Hugging Face commit и не доказывает соответствие файлов модели индексу.
Commit записывайте при скачивании через `--revision <commit>`; для имеющихся файлов
с неизвестным происхождением сохраните сами файлы и их контрольные суммы, а происхождение
отметьте как неподтверждённое. Не угадывайте ревизию по имени каталога.

Снимайте паспорт и отдельную копию весов в том же окне обслуживания, что и backup,
при остановленных изменениях конфигурации и моделей. После копирования проверьте
контрольные суммы в месте хранения. При восстановлении сверяйте паспорт с backup
до запуска приложения. Для embedding должны совпадать модель, ревизия, размерность
и параметры, влияющие на векторы. Недоступность исходной embedding-модели требует
отдельного плана миграции и переиндексации; смена имени в настройках не восстанавливает
совместимость с прежними векторами.

## Создание и проверка бэкапа

Перед началом убедитесь, что Compose-стек запущен, есть свободное место для нового
архива и настроено место хранения за пределами хоста. Пример настройки remote,
локального пути и алертов — `scripts/operations/operations.env.example`.

```bash
./scripts/operations/backup.sh
```

При отсутствии `BACKUP_REMOTE` копия остаётся только в локальном `backups/` (или в
пути `BACKUP_DIR`). Успешное завершение означает, что локальная целостность архива
проверена и логический dump восстановлен в отдельном временном PostgreSQL. Если
задан `BACKUP_REMOTE`, скрипт после локальной проверки копирует каталог через rsync;
передавайте `BACKUP_REMOTE` как достижимую цель rsync с настроенным доступом.

Проверить копию повторно, не меняя production:

```bash
BACKUP_DIR=/path/to/backups/20261103T030000Z.example
./scripts/operations/restore-check.sh "$BACKUP_DIR"
```

Проверка валидирует SHA256, структуру tar и фактический импорт `postgres.dump` во
временный PostgreSQL-контейнер. Она не проверяет запуск восстановленных Qdrant и
MinIO и не является полной репетицией аварийного переключения.

## Восстановление полного локального состояния

Не восстанавливайте поверх единственной копии рабочих данных. Если хост доступен,
сначала сохраните текущее состояние и зафиксируйте версии образов, прежде чем менять
точки монтирования.

1. Выберите архив и подтвердите его целостность и логическую восстанавливаемость:

   ```bash
   BACKUP_DIR=/path/to/backups/20261103T030000Z.example
   ./scripts/operations/restore-check.sh "$BACKUP_DIR"
   ```

2. Сверьте `release.env`, `images.txt` и [паспорт моделей](#учёт-версий-моделей)
   с планируемыми версиями. Физический каталог
   PostgreSQL запускайте совместимым образом PostgreSQL; не считайте dump проверкой
   совместимости любой версии приложения или схемы.

3. Распакуйте архив в новый staging-каталог. Каталог назначения обязан ещё не
   существовать:

   ```bash
   BACKUP_DIR=/path/to/backups/20261103T030000Z.example
   RESTORE_DIR=/path/to/restore-staging-2026-11-03
   ./scripts/operations/restore.sh "$BACKUP_DIR" "$RESTORE_DIR"
   ```

   Скрипт проверяет SHA256 и только распаковывает `data.tar.gz`; он не импортирует
   `postgres.dump`, не меняет активные Compose mounts и не переключает production.

4. Остановите трафик и все контейнеры, которые используют восстанавливаемые каталоги.
   Из корня репозитория production Compose можно остановить командой:

   ```bash
   source scripts/operations/compose.sh
   compose stop
   ```

   Сохраните нынешние каталоги `data/postgres`, `data/qdrant_storage`, `data/minio` и
   `data/redis` в отдельное имя/каталог; не удаляйте их. Перенесите соответствующие
   каталоги из staging на пути, указанные в Compose, либо примените заранее
   подготовленное изменение mount-путей. Сначала проверьте, что исходные каталоги
   сохранены и staging находится на том же файловом разделе для безопасного
   переименования.

5. Восстановите согласованные `server/.env`, `server/.env.secrets`, `client/.env`,
   PostgreSQL config/init и сетевые/TLS-настройки из отдельной защищённой копии.
   Не используйте secrets из другого окружения. Проверьте владельцев данных для
   контейнеров; после переключения при остановленных сервисах можно применить
   `sudo ./scripts/operations/data-permissions.sh` и сверить права доступа.

6. Настройте Compose на образы из `release.env` (если он есть) и согласованные
   env-файлы. Запустите сначала хранилища и дождитесь их health status, затем
   совместимую версию приложения. Из корня репозитория:

   ```bash
   source scripts/operations/compose.sh
   compose up -d --wait postgres redis qdrant minio ollama
   ```

   До запуска API/worker восстановите модели, исключённые из архива данных.
   Для локального TEI верните согласованные с корпусом веса, конфигурацию и
   токенизаторы в `data/tei_cache/bge-m3` и `data/tei_cache/bge-reranker-v2-m3`.
   Для Ollama восстановите `data/ollama_models` из отдельной копии или скачайте
   требуемую модель через `compose exec ollama ollama pull <model>`.
   Не подменяйте embedding-модель другой ревизией при восстановлении индекса.

   Если используется профиль TEI, запустите его сервисы и дождитесь health status
   **до** запуска приложения:

   ```bash
   compose up -d --wait tei-embed tei-rerank
   ```

   Затем запустите приложение:

   ```bash
   compose up -d --wait server worker client
   ```

   Деплойная версия запускает миграции перед API и worker.
   Проверьте `/api/ready`, логи API/worker, статус заданий и доступность документов.
   Выполните контролируемый поиск и вопрос в чате до возвращения пользовательского
   трафика.

7. Сохраните прежние каталоги и исходный архив до завершения проверки и согласования
   восстановления. Удаляйте старые копии только по установленной политике хранения.

Процедура выше описывает порядок переключения, а не атомарную команду: штатный
`restore.sh` намеренно не заменяет рабочие каталоги. Конкретный cutover зависит от
размещения дисков и используемого release; сначала отработайте его на staging.

## Восстановление только PostgreSQL

`postgres.dump` создан для логического восстановления и регулярно проверяется в
изолированном контейнере. `restore.sh` не загружает этот dump в рабочую БД. Не
запускайте `pg_restore --clean` на существующей production-БД как способ быстрого
отката: это может удалить более новые объекты и записи. Подготовьте пустую совместимую
БД или отдельный recovery-контур, восстановите туда dump, проверьте Alembic revision
и данные, затем спланируйте контролируемое переключение. Если PostgreSQL восстановлен
из `data.tar.gz`, не накатывайте поверх него тот же dump повторно.

## После восстановления

- Проверьте HTTP readiness и состояние основных Compose-сервисов.
- Убедитесь, что API и worker используют согласованный образ и runtime-конфигурацию.
- Проверьте один документ из MinIO/Qdrant и путь от списка документов до поиска и
  выдачи источника; отдельно убедитесь в корректности ACL для затронутых ролей.
- Проверьте завершение фоновых заданий и ошибки в логах.
- Создайте новую резервную копию после стабилизации и проверьте её отдельным
  `restore-check.sh`.
