# Эксплуатация

Руководство рассчитано на single-host Compose deployment проекта. При использовании
внешней PostgreSQL, Qdrant, S3 или ML-провайдера замените команды резервирования и проверки
на процедуры соответствующего провайдера. Bootstrap и runtime-параметры описаны в
[конфигурации](configuration.md), восстановление состояния — в
[runbook восстановления](recovery.md).

## Проверка состояния

Для production Compose используется `scripts/operations/compose.sh`. Функция
`compose` собирает Compose-команду с production-файлами и env-конфигурацией:

```bash
source scripts/operations/compose.sh
compose ps
compose logs --tail=200 server worker
```

Основные HTTP-проверки доступны через клиентский nginx:

```bash
curl --fail --silent --show-error http://127.0.0.1:3001/api/ready
curl --fail --silent --show-error http://127.0.0.1:3001/api/health
```

`/api/ready` возвращает ошибку HTTP, если приложение не готово с учётом внешних
зависимостей; `/api/health` возвращает сводку состояния API, БД, Qdrant и LLM.
`/api/live` проверяет только процесс backend и не подтверждает доступность зависимостей.
Если проверка не проходит, сначала сопоставьте статус контейнеров, время ошибки и
логи `server`, `worker`, `postgres`, `qdrant`, `redis`, `minio` и выбранного ML-сервиса.

Проверяйте свободное место и размер данных до заполнения диска:

```bash
df -h data
du -sh data/*
```

Не удаляйте вручную файлы из `data/` и не используйте `task clean` на production:
эта команда удаляет локальные данные PostgreSQL, Qdrant и Redis.

## Деплой приложения

Перед production-деплоем создайте и проверьте резервную копию в окно обслуживания
(см. [резервное копирование](recovery.md#создание-и-проверка-бэкапа)). Затем
запустите deploy-скрипт из корня проекта:

```bash
./deploy/deploy.sh 0.6.0
# Для GPU-сборки:
./deploy/deploy.sh 0.6.0 --gpu
```

Скрипт скачивает образы, оставляет работающие инфраструктурные контейнеры без
пересоздания, запускает миграции и обновляет `server`, `worker` и `client`. В конце
проверяется тот же путь `/api/ready`, которым пользуются внешние клиенты. Успешная
версия записывается в `.deploy/current.env`.

При ошибке deploy пытается вернуть прежние образы только если версия схемы БД не
изменилась либо явно задано `DEPLOY_SCHEMA_BACKWARD_COMPATIBLE=true`. Если схема
изменилась или её состояние нельзя проверить, автоматический откат блокируется.
Не обходите это ограничение принудительным запуском старого приложения поверх
непроверенной схемы; сначала сверяйте миграцию и план восстановления.

Обычные обновления приложения не обновляют образы PostgreSQL, Redis, Qdrant,
MinIO: инфраструктурное обновление планируется и проверяется отдельно.
Изменение env-файлов, которое влияет на создание контейнера или публикацию портов,
требует пересоздания соответствующих контейнеров, а `docker compose restart` этого
не делает.

## Первый ввод production-окружения

До передачи пользовательского трафика:

1. Подготовьте `server/.env`, `server/.env.secrets` и `client/.env`; задайте
   `ADMIN_EMAIL` и `ADMIN_PASSWORD` для bootstrap-учётной записи и храните секреты вне
   Git. Если используется внешний TLS/reverse proxy, проверьте маршрут до клиентского
   nginx и сохранение префикса `/api`.
2. Подготовьте production Compose и выбранный release, затем установите закреплённую
   версию через [`deploy.sh`](../../deploy/deploy.sh). Скрипт запускает миграции; для
   последующих обновлений автоматический rollback не заменяет проверку совместимости
   схемы БД.
3. Проверьте `/api/ready` и `/api/health` через тот адрес, которым будут пользоваться
   клиенты. Войдите под администратором, загрузите небольшой контрольный документ,
   дождитесь `done`, затем проверьте поиск и чат.
4. Настройте резервное копирование и алерты по разделу ниже. После первой копии
   проверьте её через `restore-check.sh` до того, как считать процедуру восстановления
   готовой.

Для внешних PostgreSQL, Qdrant и S3 настройте отдельные процедуры резервирования у
провайдера; локальные Compose-скрипты не покрывают эти сервисы. При сбое диагностику
начинайте с [runbook инцидентов](troubleshooting.md).

## Резервные копии и периодические проверки

Создать холодную согласованную копию вручную:

```bash
./scripts/operations/backup.sh
```

Скрипт берёт общий lock с деплоем, останавливает `server`, `worker` и `client`,
создаёт PostgreSQL dump, затем останавливает запущенные сервисы для копирования
каталогов хранения. После архивации исходно работающие сервисы поднимаются обратно.
На время процедуры пользовательский трафик будет прерван. После запуска скрипт
проверяет checksum и выполняет пробное восстановление PostgreSQL в изолированный
временный контейнер.

По умолчанию каталог копий — `backups/` в корне репозитория. Для удалённой копии
задайте `BACKUP_REMOTE` в `.operations.env`; если переменная не задана, скрипт явно
сообщает, что копия осталась только локальной. Образец переменных находится в
`scripts/operations/operations.env.example`. Храните backup и env-файлы с ключами в
защищённом месте; скрипты архивации сами не шифруют копию.

Установка шаблонов systemd рассчитана на корень `/opt/rag-assistant`:

```bash
cp scripts/operations/operations.env.example .operations.env
chmod 600 .operations.env
sudo cp deploy/systemd/rag-backup.service deploy/systemd/rag-backup.timer \
  deploy/systemd/rag-check.service deploy/systemd/rag-check.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rag-backup.timer rag-check.timer
systemctl list-timers rag-backup.timer rag-check.timer
```

Перед включением таймеров заполните `.operations.env` и проверьте пути/владельца
установки. Backup запускается ежедневно в 03:00 по локальному времени systemd;
health-check запускается при загрузке и затем каждые пять минут. Результат смотрите
через `journalctl -u rag-backup.service` и `journalctl -u rag-check.service`.

`check_health.py` проверяет `/api/ready`, свободное место в файловой системе `data/`
и возраст отметки последней успешной копии. Значения по умолчанию: минимум 15% места,
максимальный возраст бэкапа 48 часов. При ошибке ненулевой код возвращается systemd;
при заданном `OPERATIONS_ALERT_WEBHOOK` скрипт также отправляет краткое сообщение.
Переменная readiness URL может указывать на публичный HTTPS endpoint, если нужно
проверять внешний reverse proxy и TLS. Health-check проверяет timestamp, а не наличие
копии на remote, срок её хранения или возможность восстановления; без `BACKUP_REMOTE`
отметка может соответствовать только локальному бэкапу.

Обслуживание runtime-настроек, проверка применённой версии и ограничения `config resync`
описаны в [руководстве по конфигурации](configuration.md).
