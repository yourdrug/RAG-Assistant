# Быстрый старт API

Полная схема текущих запросов и ответов доступна в Swagger: для локального
Compose-окружения откройте `http://localhost:8001/docs`. Примеры ниже показывают
основные интеграционные сценарии; схемы FastAPI остаются источником точных полей и
ограничений.

## Адрес и аутентификация

При прямом локальном обращении к backend используйте базовый адрес
`http://localhost:8001`. Через клиентский nginx и внешний reverse proxy API обычно
доступен с префиксом `/api`, например `https://rag.example.org/api`. Не добавляйте
этот префикс к адресу backend, если обращаетесь к нему напрямую.

Для примеров задайте адрес своей инсталляции и токен после входа:

```bash
export RAG_API_BASE='http://localhost:8001'
export RAG_TOKEN='<access_token>'
```

Внутренний пользователь получает JWT через `POST /auth/login`:

```bash
curl --fail-with-body --silent --show-error \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.org","password":"<password>"}' \
  "$RAG_API_BASE/auth/login"
```

Возьмите `access_token` из ответа и передавайте его как
`Authorization: Bearer <access_token>`. Для client-аккаунта, которому выдан API-ключ,
используйте `Authorization: Api-Key <key>`. Не сохраняйте ключи в примерах, истории
команд или репозитории.

## Синхронный чат

`POST /chat/sync` возвращает готовый JSON-ответ. `question` обязателен и ограничен
16 000 символами. `conversation_id` передавайте, чтобы продолжить существующий
диалог; `depth` может быть `narrow` или `broad`. `as_of_date` — необязательная дата
в формате `YYYY-MM-DD`; если её не передать, система может вывести дату из вопроса.

```bash
curl --fail-with-body --silent --show-error \
  -H "Authorization: Bearer $RAG_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"question":"Какие правила применяются к этому вопросу?","depth":"narrow"}' \
  "$RAG_API_BASE/chat/sync"
```

Ответ содержит `answer`, `conversation_id`, `sources` и сведения об использовании
токенов. Для продолжения отправьте новый вопрос с возвращённым `conversation_id`.
Если LLM недоступна, синхронный endpoint возвращает `503` и `Retry-After: 30`.

Пример HTTP `200` (текст, ID и счётчики условные):

```json
{
  "answer": "Заявки принимаются по вторникам до 15:00 [1].",
  "conversation_id": 42,
  "sources": [
    {
      "source": "startup-check.txt",
      "pages": [],
      "document_id": 17
    }
  ],
  "confidence": null,
  "input_tokens": 320,
  "output_tokens": 24
}
```

У источников могут быть дополнительные метаданные. `sources`, `confidence` и счётчики
токенов могут быть `null`; клиент должен обрабатывать этот случай. Для следующего
вопроса в этом разговоре передайте `"conversation_id": 42`.

## Потоковый чат через SSE

`POST /chat` принимает тот же JSON, но отдаёт Server-Sent Events. Используйте
`curl -N`, чтобы клиент не буферизовал поток:

```bash
curl -N --fail-with-body \
  -H "Authorization: Bearer $RAG_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"question":"Найди применимые требования"}' \
  "$RAG_API_BASE/chat"
```

События передаются отдельными SSE-кадрами, разделёнными пустой строкой. Поле `data`
содержит JSON:

| Событие | Данные | Значение |
|---|---|---|
| `message` (тип по умолчанию) | `{"text":"..."}` | Фрагмент ответа. |
| `status` | `{"stage":"..."}` | Этап обработки. |
| `done` | `conversation_id`, `sources`, `confidence`, `as_of_date`, `request_id` | Итоговые метаданные; `sources` может быть `null`. |
| `error` | `{"error":"...","code":"..."}` | Терминальная ошибка потока. |

Кадры-комментарии вида `: heartbeat` не являются событиями и должны игнорироваться.
Ошибка, возникшая после начала потока, приходит как `event: error` при HTTP `200`;
клиенту нужно проверять события, а не только код HTTP.

## Точный поиск

`POST /search/exact` ищет текстовое совпадение в доступных пользователю чанках. Запрос
должен содержать не менее трёх символов; `mode` — `exact` (ранжированный поиск) или
`icontains` (обычный поиск вхождения). `limit` по умолчанию равен 20 и не может
превышать 100; `offset` задаёт смещение страницы.

```bash
curl --fail-with-body --silent --show-error \
  -H "Authorization: Bearer $RAG_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"query":"срок вступления в силу","mode":"exact","limit":20,"offset":0}' \
  "$RAG_API_BASE/search/exact"
```

Ответ содержит `results`, `total`, `limit` и `offset`. Результаты уже ограничены
областью доступа пользователя; `document_id` можно передать для поиска внутри одного
документа.

Пример HTTP `200` для запроса выше (данные условные):

```json
{
  "query": "срок вступления в силу",
  "results": [
    {
      "chunk_id": 123,
      "document_id": 17,
      "filename": "regulation.txt",
      "content": "Срок вступления в силу правила — следующий день после опубликования.",
      "chunk_index": 0
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

`total` — общее число совпавших чанков в доступной области, а `results` — текущая
страница. При отсутствии совпадений возвращаются `results: []` и `total: 0` с HTTP `200`.

## Загрузка и удаление документа

`POST /documents` принимает `multipart/form-data` и требует права управления
документами. Пример загрузки во внутренний общий корпус:

```bash
curl --fail-with-body --silent --show-error \
  -H "Authorization: Bearer $RAG_TOKEN" \
  -F 'file=@./document.pdf' \
  -F 'visibility=internal_public' \
  "$RAG_API_BASE/documents"
```

Для `internal_group` укажите `group_id`; для `client_private` — `client_id`, если
загружает внутренний пользователь. При стандартной конфигурации принимаются файлы
`.pdf`, `.docx`, `.rtf`, `.md` и `.txt`; список расширений и лимит размера задаются
конфигурацией. Стандартный лимит — 50 MiB. Пустой файл, несовпадение расширения с
содержимым и неподдерживаемый формат приводят к ошибке валидации; превышение лимита —
к `413`.

Ответ содержит `document_id`, `filename` и статус постановки обработки. Дальше
проверяйте документ через `GET /documents/{document_id}`. Различие статусов `processing`,
`indexing`, `done` и `failed` описано в [пользовательских сценариях](../usage/user-scenarios.md#просмотреть-и-загрузить-документы).

Удаление асинхронное: `DELETE /documents/{document_id}` возвращает `202 Accepted` и
`job_id`. Проверяйте выполнение через
`GET /documents/{document_id}/deletion/{job_id}`.

## Коды ошибок и доступ

| Код | Частая причина |
|---|---|
| `400` | Например, пустой вопрос чата. |
| `401` | Нет действительного JWT или API-ключа. |
| `403` | У пользователя нет нужной роли, capability или доступа к объекту. |
| `413` | Загрузка превышает настроенный лимит размера. |
| `422` | Ошибка схемы, неподдерживаемый формат или содержимое файла не соответствует расширению. |
| `503` | Синхронный чат не может обратиться к LLM; учитывайте `Retry-After`. |

Например, запрос `POST /search/exact` с JSON `{"query":"аб"}` и действительной
аутентификацией возвращает HTTP `422`:

```json
{
  "message": "Ошибка валидации",
  "errors": {
    "query": "Минимум 3 символов"
  }
}
```

HTTP-ошибки используют поле `message` и могут содержать словарь `errors` с деталями
по полям. Это формат обработчика приложения; SSE-ошибки имеют отдельный формат
`{"error":"...","code":"..."}`, описанный выше.

Для полного перечня маршрутов, ограничений и ответов откройте Swagger для своей
инсталляции. В production используйте HTTPS и передавайте только те полномочия,
которые нужны интеграции.
