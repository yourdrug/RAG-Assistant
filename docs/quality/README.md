# Оценка качества RAG

Benchmark нужен для повторяемого сравнения retrieval и ответов на фиксированном
наборе вопросов. Результат зависит от набора, разметки, снимка runtime-конфигурации,
провайдера и модели-судьи; сравнивайте запуски при одинаковых условиях.

## Подготовка набора вопросов

В интерфейсе откройте **Admin → Quality / Benchmark**. Вопросы хранятся в наборах
(`dataset`, имя `<pack>-<назначение>`: `belarus_law-main`, `belarus_law-quick`,
`support-main`, `support-quick`; по умолчанию `belarus_law-main`); неактивные вопросы в оценку не включаются. Для
воспроизводимого набора сохраняйте одинаковые формулировки и эталонные метки между
запусками.

У вопроса могут быть `expected_answer`, `source_hint`, `annotations`, `history` и
`as_of_date`. `source_hint` помогает проверить, появился ли документ с указанным
именем среди результатов. Для более точной оценки retrieval и контекста используйте
`annotations`, например:

```json
{
  "question": "Когда вступает в силу указанное правило?",
  "expected_answer": "Со следующего дня после официального опубликования.",
  "source_hint": "regulation.pdf",
  "annotations": {
    "expected_fragments": [
      {
        "source": "regulation.pdf",
        "text": "Настоящее правило вступает в силу со дня, следующего за днём официального опубликования.",
        "pages": [3]
      }
    ],
    "required_facts": ["со следующего дня после опубликования"],
    "required_conditions": []
  }
}
```

У ожидаемого фрагмента обязательны `source` и `text`; необязательные поля могут
уточнять страницы, раздел или идентификаторы документа и редакции. Факты и условия
задаются непустыми фразами; список фраз внутри одного элемента означает допустимые
альтернативы. Набор аннотаций ограничен 100 фрагментами и 100 требованиями каждого
типа. Ссылки на эталонный ответ и аннотации используются оценщиком и не передаются
генератору как подсказка.

Старайтесь включать в набор обычные вопросы, запросы с датой редакции, случаи с
несколькими необходимыми фактами и вопросы, для которых корректен отказ от ответа.
Проверьте, что указанные фрагменты действительно есть в доступном корпусе. Не
помещайте в набор секреты или персональные данные: вопросы, ответы и экспорты
сохраняются как benchmark-данные.

Источник вопросов — только БД. Резервная копия набора — экспорт из админки
(`GET /admin/benchmark/questions/export`), загрузка — импорт того же формата;
структуру выгрузки проверяет `task benchmark:validate -- export.json`.
В пакетах предметной области лежат лишь офлайн-подмножества для проверки chunking
(`benchmarks/chunking/*.json`).

### Класс ответа

`annotations.answer_type` задаёт, какой ответ считается успешным, и выбирает рубрику
судьи; `annotations.expected_behavior` обязан ему соответствовать
(`ANSWER_BEHAVIORS` в [question.py](../../server/app/domain/benchmark/question.py)).

| `answer_type` | `expected_behavior` | Успешный ответ |
|---|---|---|
| `factual` | `answer` | Правильный содержательный ответ, подтверждённый источником |
| `negative` | `answer` | Явное «нет» с объяснением по источнику, а не «информация не найдена» |
| `false_premise` | `correct_premise` | Указывает на неверную предпосылку (несуществующий пункт, форму, поле) и не выдумывает детали |
| `not_in_corpus` | `abstain` | Честный отказ: нужных сведений в корпусе нет |
| `out_of_scope` | `abstain` | Не отвечает на постороннюю задачу так, будто она подтверждена базой |
| `ambiguous` | `clarify_ambiguity` | Объясняет неоднозначность и ограничения источника |

`false_premise` не равен `not_in_corpus`: на вопрос о несуществующем поле ответ
«сведений не найдено» неверен — нужно сказать, что такого поля нет. Так же `negative`
нельзя засчитывать как удачный отказ. Для `not_in_corpus` и `out_of_scope` retrieval-метрики
по эталонным фрагментам неприменимы. Без `answer_type` действует совместимость:
`expected_refusal=true` → `not_in_corpus`, иначе `factual`.

`case_id` — устойчивый идентификатор семантически одинакового вопроса: повтор в другом
наборе имеет тот же `case_id`, перефразировка — свой `case_id` и `variant_of` исходного.
При объединении наборов результаты дедуплицируются по `case_id`.

### Состав приёмочного набора

Набор `<pack>-main` — 40–60 активных вопросов: ≥ 50% фактических с `expected_fragments`,
≥ 15% с несколькими `required_facts`, ≥ 15% с корректным отказом (`not_in_corpus`,
`out_of_scope`), ≥ 10% с `history`; для `belarus_law` ещё ≥ 10% с `as_of_date`.
Проверка: `GET /admin/benchmark/datasets/{dataset}/composition` или
`task benchmark:validate -- export.json --composition belarus_law-main`.

## Классы ошибок

Каждый результат вопроса получает класс (`domain/benchmark/diagnosis.py`); класс
пересчитывается из сохранённых метрик при чтении, поэтому старые прогоны тоже классифицированы.
Проверки идут по стадиям, первая неуспешная — причина:

| Класс | Условие |
|---|---|
| `retrieval_miss` | `fragment_recall_at_k < 1` (без фрагментов — `retrieval_fact_coverage < 1`) |
| `false_refusal` | исход `not_found`/`out_of_domain`/блокировка, а вопрос размечен как отвечаемый |
| `context_loss` | найдено поиском, но `context_fragment_recall < fragment_recall_at_k` |
| `generation_error` | контекст полон, но `correctness` или `faithfulness` < 7 |
| `false_answer` | ожидался отказ (`not_in_corpus`, `out_of_scope`), а дан ответ и `refusal_score` < 7 |
| `unlabeled` | нечем проверить: нет аннотаций и оценок либо аннотации невалидны |
| `ok` | остальное |

Сводка прогона содержит `diagnosis_counts` и `false_answer_rate`; сравнение прогонов
(`GET /admin/benchmark/runs/compare`) — матрицу переходов классов по вопросам.

## Приёмка и регрессия

Пороги приёмки набора хранятся в БД (`benchmark_dataset_policies`, редактируются в
админке): минимумы `fragment_recall_at_k`, `context_fragment_recall`, `correctness`
и максимум `false_answer_rate`. `task bench:regression` (CLI `benchmark regression`)
проверяет последний прогон набора `<pack>-quick` каждого зарегистрированного пакета (пакет без
такого набора — `insufficient_data`); `-d <набор>` выбирает наборы явно:

1. пороги приёмки — по всему прогону;
2. сравнение с baseline — только по вопросам, чьё содержимое (`question_hash`:
   вопрос, история, дата, эталон, аннотации) не менялось; изменённые, новые и удалённые
   вопросы перечисляются и исключаются. Baseline без хешей на другом наборе вопросов
   не сравнивается.

Итог — `passed`, `failed` (exit 1) или `insufficient_data` (exit 2): нет прогона, нет
совместимого baseline (тот же корпус, пространство и судья — модель и версия рубрики), не
осталось неизменённых вопросов или отсутствует метрика с заданным порогом. Отсутствие данных
не считается успехом.

**Текущие пороги (заданы 2026-11-18, до baseline).**

| Набор | min `fragment_recall_at_k` | min `context_fragment_recall` | min `correctness` | max `false_answer_rate` |
|---|---|---|---|---|
| `belarus_law-main` | 0.60 | 0.50 | 6.0 | 0.10 (1 из 11 отказов) |
| `belarus_law-quick` | 0.55 | 0.45 | 6.0 | 0.17 (1 из 6) |
| `support-main`, `internal-main` | 0.85 | 0.80 | 7.5 | 0.13 (1 из 8) |
| `support-quick`, `internal-quick` | 0.80 | 0.75 | 7.0 | 0.25 (1 из 4) |

Почему такие:

- Пороги — нижняя граница от явной поломки, а не цель. Регрессии ловит сравнение с baseline
  (2σ, до замера σ — допуски по умолчанию: 0.05 для recall, 1.0 балла для оценок судьи).
- Право: прогон `quick` 2026-10-07 на прежнем стеке (qwen2.5:7b) дал `fragment_recall_at_k` 0.72,
  `context_fragment_recall` 0.60, `correctness` 7.2. Минимумы на 0.10–0.12 ниже: в `-quick`
  ~24 вопроса с фрагментами, один вопрос ≈ 0.04, запас ≈ 3 вопроса от шума. У `-quick` пороги
  на 0.05 ниже `-main` — вопросов меньше, разброс больше.
- `context_fragment_recall` ниже recall поиска: часть найденного теряется на реранкере и
  бюджете контекста.
- `correctness` 6.0: судья считает ответ верным с 7; минимум 6 — средний ответ не хуже
  пограничного (прежний стек — 7.2).
- `support`/`internal`: корпус ~24 чанка на пакет, поиск почти тривиален, synthetic-наборы давали
  `correctness` 9.5–10. Запас ≈ 5 вопросов оставлен под уточнения с `history`, которые сложнее.
- `false_answer_rate` считается только по вопросам с ожидаемым отказом; допускается одна
  ошибка на набор. Ноль срабатывал бы от разброса судьи в оценке отказа (`refusal_score` ≥ 7).
- После baseline и замера σ минимумы пересчитать как baseline − max(2σ, один вопрос).

**Достижимость фрагментов.** `task bench:reachability -- -d <набор>` (или
`GET /admin/benchmark/datasets/{dataset}/reachability`) проверяет без LLM, что каждый
`expected_fragment` активных вопросов целиком лежит в одном чанке пространства пакета (по тем же
правилам совпадения, что и `fragment_recall_at_k`). `no_document` — файла нет в пространстве,
`not_in_chunk` — файл есть, но фрагмент разрезан или не совпадает с текстом. Вопрос с
недостижимым фрагментом измеряет разметку или загрузку, а не поиск; проверка обязательна перед
снятием baseline.

**Правило значимости.** Изменение метрики значимо, если превышает 2σ — стандартного
отклонения трёх прогонов одной конфигурации (`benchmark noise -d <dataset> --repeat 3`
или по уже готовым прогонам: `--run-id … --run-id …`). σ хранится вместе с моделью и
версией рубрики судьи; если судья сменился, σ недействительна, регрессия предупреждает
и использует пороги по умолчанию.

**Калибровка судьи.** В результатах прогона ответы размечаются вручную
(`correctness`/`faithfulness` 0–10, 30–50 ответов на пакет, смесь хороших и плохих по
классам ошибок). Согласие судьи с людьми — MAE, Spearman и Cohen κ по порогу 7
(`GET /admin/benchmark/runs/{id}/agreement`); сохраняется в политику набора. При κ < 0.6
сначала чинят промпт или модель судьи, а не пайплайн. Калибровку повторяют при смене судьи.

## Гейт регрессий

- **Офлайн, каждый PR, трогающий ingestion/chunking/retrieval:** `task quality:offline-gate`
  — нарезка, достижимость фрагментов и BM25 recall/MRR каждого пакета против эталонов
  `docs/quality/artifacts/offline-gate/<pack>.json` (допуск 0.02), плюс `acceptance.json`
  пакетов. Без LLM и платных вызовов. Корпуса `support` и `internal` лежат в репозитории
  и проверяются в CI (job `offline-gate` в `.github/workflows/lint.yml`); корпус `belarus_law`
  локальный — для него прогон обязателен у автора PR, отчёт прикладывается к PR. Dense recall
  (`task chunking:report -- --dense`) платный и в гейт не входит: запускается автором PR,
  если меняется embed-текст или нарезка. Осознанное изменение нарезки обновляет
  эталон в том же PR: `task quality:offline-reference PACK=<pack>`.
- **Онлайн, вручную перед слиянием PR, меняющего RAG/промпты/модели:** прогон платный,
  запускается, когда PR готов целиком: `task bench -- -d <pack>-quick` для всех пакетов,
  затем `task bench:regression` (без аргументов проверяет `-quick` всех пакетов). Run id и переходы классов — в описание PR. Полный `-main`
  — по решению автора.
- **После выкатки:** сводка журнала по `config_hash` — доля 👎, `not_found` и латентность
  за 3–7 дней до и после.

## Рекомендуемый цикл сравнения

1. Подготовьте небольшой стабильный набор, проверьте формулировки и аннотации.
2. Запустите baseline и сохраните ID запуска, набор, снимок конфигурации и модель-судью.
3. Измените один retrieval-параметр или компонент за раз, затем повторите тот же набор
   в тех же условиях.
4. Сравните сводные метрики и результаты по каждому вопросу. Разберите изменившиеся
   ответы и диагностические данные, а не только итоговый composite score.
5. Используйте sweep для поиска конфигурации по нескольким параметрам. Режим `fast`
   сначала оценивает retrieval и ограниченный shortlist ответов; `full` запускает RAG
   и judge для каждой комбинации grid и обычно требует больше времени и вызовов модели.

Benchmark можно запускать из административного интерфейса. Для интеграций доступны
API запуска `POST /benchmark`, чтения результатов `/benchmark/results` и экспорта
`/benchmark/results/{run_id}/export`; sweep API описан в Swagger. Для сохранения
устойчивых артефактов используйте `docs/quality/artifacts/`, не коммитьте в Git сырые
выгрузки с пользовательскими данными. Пример экспорта через CLI находится в
[индексе документации](../README.md).

## Как читать метрики

| Метрика | Что показывает | Требуемая разметка и ограничение |
|---|---|---|
| `hit_rate`, `mrr` | Нашёлся ли ожидаемый источник и насколько высоко он ранжирован. | Нужен `source_hint`; сопоставление имени файла не проверяет точность фрагмента. Без метки результат недоступен (`null`), а не равен нулю. |
| `fragment_recall_at_k`, `fragment_mrr` | Найдены ли ожидаемые фрагменты и их позиция в retrieval-результатах. | Нужны `expected_fragments`; значение от 0 до 1. |
| `retrieval_fact_coverage` | Покрытие обязательных фактов найденными документами. | Нужны `required_facts`; фразы оцениваются лексически. |
| `context_fragment_recall`, `context_fact_coverage` | Сохранил ли отобранный контекст размеченные фрагменты и факты. | Нужны аннотации; проверка покрытия лексическая, поэтому это диагностическая оценка, а не семантическое доказательство. |
| `faithfulness`, `relevancy`, `correctness` | Оценка верности ответа контексту, соответствия вопросу и ожидаемому ответу. | Оценивает LLM-судья по шкале 0–10; для `correctness` задайте `expected_answer`. Судья может ошибаться. |

Смотрите также число оценённых вопросов, недоступные метрики, ошибки judge и статус
проверки аннотаций. Усреднение может скрыть отдельные регрессии: откройте детали по
каждому вопросу и проверьте конкретный ответ, контекст и источники.
