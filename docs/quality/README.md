# Оценка качества RAG

Benchmark нужен для повторяемого сравнения retrieval и ответов на фиксированном
наборе вопросов. Результат зависит от набора, разметки, снимка runtime-конфигурации,
провайдера и модели-судьи; сравнивайте запуски при одинаковых условиях.

## Подготовка набора вопросов

В интерфейсе откройте **Admin → Quality / Benchmark**. Вопросы хранятся в наборах
(`dataset`, по умолчанию `main`); неактивные вопросы в оценку не включаются. Для
воспроизводимого набора сохраняйте одинаковые формулировки и эталонные метки между
запусками.

У вопроса могут быть `expected_answer`, `source_hint`, `annotations`, `history` и
`as_of_date`. `source_hint` помогает проверить, появился ли документ с указанным
именем среди результатов. Для более точной оценки retrieval и контекста используйте
`annotations`, например:

```json
{
  "question": "Когда вступает в силу указанное правило?",
  "expected_answer": "Со следующего дня после официального опубликования.",
  "source_hint": "regulation.pdf",
  "annotations": {
    "expected_fragments": [
      {
        "source": "regulation.pdf",
        "text": "Настоящее правило вступает в силу со дня, следующего за днём официального опубликования.",
        "pages": [3]
      }
    ],
    "required_facts": ["со следующего дня после опубликования"],
    "required_conditions": []
  }
}
```

У ожидаемого фрагмента обязательны `source` и `text`; необязательные поля могут
уточнять страницы, раздел или идентификаторы документа и редакции. Факты и условия
задаются непустыми фразами; список фраз внутри одного элемента означает допустимые
альтернативы. Набор аннотаций ограничен 100 фрагментами и 100 требованиями каждого
типа. Ссылки на эталонный ответ и аннотации используются оценщиком и не передаются
генератору как подсказка.

Старайтесь включать в набор обычные вопросы, запросы с датой редакции, случаи с
несколькими необходимыми фактами и вопросы, для которых корректен отказ от ответа.
Проверьте, что указанные фрагменты действительно есть в доступном корпусе. Не
помещайте в набор секреты или персональные данные: вопросы, ответы и экспорты
сохраняются как benchmark-данные.

## Рекомендуемый цикл сравнения

1. Подготовьте небольшой стабильный набор, проверьте формулировки и аннотации.
2. Запустите baseline и сохраните ID запуска, набор, снимок конфигурации и модель-судью.
3. Измените один retrieval-параметр или компонент за раз, затем повторите тот же набор
   в тех же условиях.
4. Сравните сводные метрики и результаты по каждому вопросу. Разберите изменившиеся
   ответы и диагностические данные, а не только итоговый composite score.
5. Используйте sweep для поиска конфигурации по нескольким параметрам. Режим `fast`
   сначала оценивает retrieval и ограниченный shortlist ответов; `full` запускает RAG
   и judge для каждой комбинации grid и обычно требует больше времени и вызовов модели.

Benchmark можно запускать из административного интерфейса. Для интеграций доступны
API запуска `POST /benchmark`, чтения результатов `/benchmark/results` и экспорта
`/benchmark/results/{run_id}/export`; sweep API описан в Swagger. Для сохранения
устойчивых артефактов используйте `docs/quality/artifacts/`, не коммитьте в Git сырые
выгрузки с пользовательскими данными. Пример экспорта через CLI находится в
[индексе документации](../README.md).

## Как читать метрики

| Метрика | Что показывает | Требуемая разметка и ограничение |
|---|---|---|
| `hit_rate`, `mrr` | Нашёлся ли ожидаемый источник и насколько высоко он ранжирован. | Нужен `source_hint`; сопоставление имени файла не проверяет точность фрагмента. Без метки результат недоступен (`null`), а не равен нулю. |
| `fragment_recall_at_k`, `fragment_mrr` | Найдены ли ожидаемые фрагменты и их позиция в retrieval-результатах. | Нужны `expected_fragments`; значение от 0 до 1. |
| `retrieval_fact_coverage` | Покрытие обязательных фактов найденными документами. | Нужны `required_facts`; фразы оцениваются лексически. |
| `context_fragment_recall`, `context_fact_coverage` | Сохранил ли отобранный контекст размеченные фрагменты и факты. | Нужны аннотации; проверка покрытия лексическая, поэтому это диагностическая оценка, а не семантическое доказательство. |
| `faithfulness`, `relevancy`, `correctness` | Оценка верности ответа контексту, соответствия вопросу и ожидаемому ответу. | Оценивает LLM-судья по шкале 0–10; для `correctness` задайте `expected_answer`. Судья может ошибаться. |

Смотрите также число оценённых вопросов, недоступные метрики, ошибки judge и статус
проверки аннотаций. Усреднение может скрыть отдельные регрессии: откройте детали по
каждому вопросу и проверьте конкретный ответ, контекст и источники.
