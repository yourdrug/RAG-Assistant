# Вертикализация `application/` и очистка линт-долга

## Оценка предложения

Направление поддерживаю: пакеты по фичам упростят навигацию. Промежуточная горизонтальная раскладка добавит второй перенос, поэтому сразу переходим к вертикальной структуре небольшими PR.

В план нужны следующие поправки:

- **Ограждение уже существует.** `import-linter`, isort и `known-first-party` настроены в [pyproject.toml](server/pyproject.toml). Дополняем контракты по мере появления фич. Правило «всем разрешён только identity/indexing» слишком узкое: уже существуют другие содержательные зависимости.
- **Шимы делаем с явными экспортами**, без `import *`. Обновляем также тестовые patch-targets: реэкспорт класса не перенаправляет подмену глобальных переменных старого модуля.
- **Авторизацию объединяем осторожно.** Rename/delete используют `check_ownership`, операции с чанками — `can_edit_chunks`. Общий загрузчик допустим, но различия разрешений, статусов и порядка проверок сохраняются.
- **Общую запись чанков отделяем от версионирования.** Помещение `persist_chunks_with_versioning` в `indexing` создаёт риск цикла с `act_versioning`. В `indexing` оставляем запись чанков и outbox; подготовку редакций предоставляет `act_versioning`, транзакциями управляют вызывающие сценарии.
- **Ветка собственного UoW не мёртвая:** её использует [тест повторной индексации](server/tests/test_reingestion_consistency.py). Переход на явный `*_in_uow` возможен отдельным изменением с переносом открытия транзакций в вызывающий код.
- **Находка с `force` требует уточнения:** `run_single` его теряет, однако [HTTP-маршрут](server/app/presentation/api/routes/ingest.py) отдельно выполняет принудительную переиндексацию. Нельзя считать весь HTTP-сценарий сломанным.

Удаление неиспользуемого `HybridRetrieverPort` обосновано. Сам `HybridRetriever` оставляем в `application/search/hybrid.py`: отсутствие I/O само по себе не требует переноса в Domain. Делегирующие фасады сохраняем, если они служат публичной границей фичи.

## Последовательность миграции

1. **Выполнено:** `uow` — первый этап, подробно описанный ниже.
2. `budget`, `admin`, `benchmark`, `act_versioning`, `identity`, `chat`, `search` — отдельными PR. Добавляем пропущенные в исходной схеме budget-сервисы, benchmark import/export, контекст биллинга и контракты конфигурации/corpus.
3. `indexing`, затем согласованные переносы `documents`, `chunks`, `ingestion`.
4. После переносов — отдельные изменения поведения: разделение AuthService, объединение ingestion-фасадов, унификация парсеров, устранение N+1 и подтверждённых дефектов.

В каждом PR перенос и содержательные изменения разделяем коммитами. Порт относится к фиче по владельцу сценария; реализации в infrastructure сами по себе не делают его общим. Кросс-фичевые потребители используют публичные экспорты и контракты, а не внутренние модули.

Публичные входные и выходные модели размещаем в `dto.py` фичи; внутренние результаты шагов могут оставаться рядом с кодом. Мутабельный processing context остаётся внутри обработки документов.

## Политика очистки линт-долга

Цель всей серии — очистить **весь `application/`**. Вне слоя меняются только необходимые потребители и контракты.

- Переносимые модули проходят проверки без файловых baseline и новых `noqa`/`type: ignore`, добавленных ради зелёного результата.
- Пороги и строгие правила сохраняются. Несовместимые сигнатуры исправляются вместе с потребителями.
- В каждом PR удаляются соответствующие исключения Ruff, mypy, форматирования, пустых строк и vulture; существующий `LINT_DEBT.md` обновляется по фактическим результатам.
- После изменения `pyproject.toml` выполняется обновление lock-файла. Новые зависимости для первого PR не нужны.
- Имеющиеся незавершённые изменения пользователя сохраняются.

## Проверки и критерии приёмки

Для первого PR добавить тесты настоящего UoW: успешный commit, rollback при ошибке и отмене, ошибка commit, ошибки rollback/close, порядок событий и привязка репозиториев. Проверить идентичность типов через старые и новые импорты и отсутствие циклов при разном порядке импорта.

Повторить целевые characterization-, persistence-, ingestion- и CLI-тесты, затем все проверки из `task lint`. В последующих этапах запускать соответствующие ACL/RAG-тесты; изменения конкурентного поведения проверять отдельно.

Исходная точка до реализации подтверждена: без временных исключений в application воспроизводятся **950 замечаний Ruff и 150 ошибок mypy**. Все семь текущих проверок линтинга выполнены напрямую и прошли с существующими baseline. Прошли **83 целевых pytest-теста** и отдельно **6 сценариев жизненного цикла UoW**.

При подготовке исходной оценки исходники не изменялись. Полный pytest и внешние интеграции не запускались; основной риск дальнейших этапов — сохранение ACL и транзакционной атомарности.
